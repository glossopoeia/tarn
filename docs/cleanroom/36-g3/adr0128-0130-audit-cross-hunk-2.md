## Operations worked to bytes

**Drop-a-layer by commit vs. by rewrite (§20.4, §20.5, hunks 26–31).** A commit dropping layer L: L's record disappears from the new directory (shape (c) per the Example, hunk 26); L's stored tiles and tile-index region, previously live, become slack (§5.2) — not reclaimed, just unclaimed; the file is no smaller; an updater that does this SHOULD report the loss (§20.4 table, unchanged wording). A rewrite dropping L: L's record, tiles and index region are simply omitted from the new file entirely (§20.5, hunk 29's "a record dropped, a layer with its index region and stored tiles among them, is not in the output"); the bytes do not exist in the output at all — the rewrite is the only operation that actually shrinks the total. Both routes are now available only because hunk 12 changed the layer record's registry-fixed flags from MU=1,PE=1 to MU=0,PE=0 — under PE=1 (old value) dropping was never licensed at all. Checked and consistent between hunks 26, 28, 29.

**A commit dropping layer L and adding a new layer under L's name (§20.3 step 4, R-CNT-13, §5.2's partition).** §20.3 step 4 fixes the writing model: "writing begins at exactly F; new stored tiles and record extents follow" (unchanged text, not itself in a hunk). So a same-commit replacement of L writes the new layer's tiles/index strictly after F; it can never address the byte range L's old tiles occupied (that range lies below F and is frozen — §9.1/R-LIF-01 — and is not "reachable" live content once L's record is gone, so a new record pointing there would not be new data, only reused old bytes). The charter's harder variant — new entries "addressing the extents L's tiles occupy" — is therefore not constructible by an appender at all; it would require a rewrite (relocation is explicitly a rewriter's operation only, per hunk 21 and hunk 5, both un-defect: "relocating a live index region is a rewriter's operation (§20.5, `[R-WRT-07]`), not an appender's"). No defect found in this operation; the text is internally consistent once R-LIF-01/§9.1 and §20.3 step 4 are read together.

**A layer record whose stored flags are MU=1,PE=1 vs MU=1,PE=0 (R-CNT-12, R-CNT-22, L46, L49).** For a registered type (layer), R-CNT-22 makes the *registry's* fixed flags (now MU=0, PE=0) govern regardless of what is stored — so functionally neither stored-flag combination changes what an updater/rewriter/reader does. But both stored combinations are separately flagged as *verifier*-detected violations: MU=1,PE=1 differs from the registry fix → L49; MU=1,PE=0 differs from the registry fix *and* is the specifically-forbidden MU=1/PE=0 combination → both L46 and L49 fire. Traced this against the live register rows (L46, L47, L49, F25, F28) at lines 3906–3909 and hunk 36's restated sentence at lines 3793–3798; citations resolve and the two mechanisms (R-CNT-22's override, R-CNT-12's MU=1/PE=0-read-as-PE=1 resolution) do not conflict — R-CNT-12's resolution is moot for a *registered* type since R-CNT-22 already fixes its effective flags, but the verifier-detection layer (L46/L49) still fires on the stored anomaly. No defect.

**§7.2's "further references" exception vs. the new layer registry flag (hunk 11 × hunk 12).** See finding Y-02 below — worked to bytes: a hypothetical tile-index-region-carrying registered type declared MU=0 in a future minor version would, by the letter of the still-standing "MU=0 ⇒ no further embedded offsets" rule, be nonconforming to carry a tile index at all, yet the *current* registered layer type does exactly that while itself being MU=0. The passage's own stated justification for the exception is now false for its own worked case.

**§20.1's two writer-tier tests, applied to a tool that decodes an existing file whole and writes a new one (hunk 19).** See finding Y-01 below — worked to the trailer's flags byte specifically, the one field whose required value genuinely forks between "creator" (flags = 0, §6.3) and "rewriter" (carry forward the input's unknown ignore-lane bits and set no other, §20.5/R-CNT-08, hunk 9).

**§20.1 read as an implementer's classification test (also charter's closing ask).** An appender that adds one layer and decodes nothing else: carries forward every other record undecoded ⇒ updater (test 1) ⇒ owes §20.4 preservation for the whole file; matches its self-description as "appender" with no tension. A rewriter that re-creates every layer: if it also carries any non-layer record (e.g. user metadata) forward without decoding it, test 1 fires (updater/rewriter, owing preservation) — consistent. If it also decodes *that* record (i.e. genuinely decodes and re-emits literally everything), test 2 fires ("creator, whatever it read") — in tension with R-LIF-01's commit/rewrite dichotomy, since it plainly took an existing file as input and produced a new file_id (this is exactly Y-01, restated from the implementer's chair as the charter asks).

**§20.4's table read as an updater deciding what it may do to each record of a two-layer file that also carries a user-metadata record.** Layer A (MU=0,PE=0): retain byte-identical, or drop (report the loss). Layer B (MU=0,PE=0): same, independently. User-metadata record (MU=0,PE=1): retain byte-identical, extent content unmodified — never droppable, at either file or layer sub-record scope (§20.4's prose paragraph, hunk 28, confirmed against the table's own PE=1 row). No row lets an updater touch fixed declarations of a layer that stored a tile except through §20.3 step 4's narrow list. This reading turned up no defect beyond Y-03/Y-04's stale-MU=1 material a few sections earlier.

## Findings detail

See structured findings for full text. Summary:

- **Y-01** (hunk 19, cross-checked against hunks 9, 13, 29, 30): §20.1's "one that decodes everything it writes is a creator, whatever it read" directly contradicts R-LIF-01 (cited in the very same paragraph), which makes any transformation of an existing file into a new one *by definition* "a whole-file rewrite... (a rewrite, §20.5)" with no creator carve-out. Byte-level: the trailer's ignore-lane flag bits are forced to 0 under one reading (§6.3's creator rule) and forced to carry the input's bits forward under the other (§20.5/R-CNT-08's rewriter rule) — for the identical tool, the identical input, and the identical decoded output.

- **Y-02** (hunk 11, defect surfaces against hunk 12): §7.2 still explains the layer record's tile index as an instance of "Records with MU = 1 carry further references..." — but hunk 12 (same commit set) changed the layer record's registry-fixed flags to MU = 0. The general MU=0 rule two sentences earlier ("the extent slot is its only sanctioned reference... neither its inline payload nor its extent contents encode offsets or lengths of other file bytes") is now falsified by the layer record itself. Not clearly byte-level for the *current* two registered types (the layer's relocate/regenerate behavior is fully and correctly re-specified in §20.5 regardless of this rationale), but the stated premise is false and would mislead a future registry reviewer.

- **Y-03** (§7.4's worked example at spec line 1206, outside any of the 49 hunks — a restatement the registry-flag hunk (12) should have swept and did not): the example's prose still says the record's "registry-fixed flags [are] MU = 1, PE = 1 (§7.3)" — now wrong; those flags are MU = 0, PE = 0. If taken literally as a conformance vector (as §4.7 requires every worked example to pair with), the described bytes would violate L49. Not byte-level in the fork sense (only one answer is correct post-repair), but a genuine unswept restatement.

- **Y-04** (hunk 46, contradicted by hunk 29's definition and inconsistent with the parallel sentence in hunk 47, same appendix item): Appendix G item 8 narrows its subject from "a rewriter" (used everywhere else in the item, including the immediately following and immediately preceding sentences) to "**A compaction's** output is therefore reproducible only modulo... the records §20.4 lets it drop... retained or dropped at the rewriter's choice" — but §20.5 (hunk 29) defines compaction as the rewrite that "carries every structure forward and changes nothing but placement," i.e., by definition it never drops anything. Non-normative appendix, not byte-level, but an internal contradiction between a term's definition and its use four sentences away.

- **Y-05** (line 438, §3.3 Note — outside any of the 49 hunks; representative rename hunk cited: hunk 02): "verifiers, appenders, and compactors" — leftover plural actor-tier name from before the rename. Non-normative Note, cosmetic, not byte-level.

- **Y-06** (hunk 49): Appendix H's "Conforming updater" checklist states "drops a layer record only under §20.4's PE = 0 licence, **reporting the loss**" as a flat item, but the underlying rule (§20.4 table) is a SHOULD, not a MUST, and the same appendix elsewhere explicitly flags SHOULD-level items as "Advisory, and not a conformance condition" rather than folding them into the plain list. Non-normative appendix, not byte-level, but a real overclaim risk for an implementer using this checklist to self-audit.

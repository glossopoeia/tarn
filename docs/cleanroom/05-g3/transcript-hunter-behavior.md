## Findings

### BYTE-LEVEL AMBIGUITY

**1. Is a nonzero pre-trailer pad / alignment gap a verifier-rejectable violation? §22.3 `[R-SEC-04]` + Appendix H say yes; §21.6 + §5.2 say no.**

- **Location.** §22.3 `[R-SEC-04]`: "Declared padding is covered by no checksum (§8.1): corruption confined to padding is invisible to a reader and **caught only by a verifier's zero check** (`[R-CNT-03]`)." Appendix H, verifier checklist: "plus the checks readers are exempt from: … **declared-padding content (§5.2)**". Upstream root: §6.2 `[R-CNT-05]` "Writers MUST place the directory so that only the **zero** pre-trailer pad … lies between the directory's end and the trailer; **a verifier MUST treat a violation as a validity error at file scope**."
- **Reading A (a zero check exists).** The pad's content is normatively zero. `[R-CNT-05]`'s adjective "zero" is part of what MUST lie in the gap; a nonzero pad means something other than "the zero pre-trailer pad" lies there, so the verifier MUST report a file-scope validity error. `[R-SEC-04]` states the check as a fact, and Appendix H lists it among the verifier's exclusive duties.
- **Reading B (no such check).** §5.2 `[R-CNT-21]`: slack — explicitly including "the pre-trailer pad" — "has no internal structure this specification defines, **its content is unconstrained, and no conformance requirement applies to it**." §5.2 `[R-CNT-03]`: writers *SHOULD* zero gaps; "**no conformance requirement rides on slack content either way**." §9.7 `[R-LIF-08]`: "Bytes the walk does not reach are slack: the verifier sums them and reports the total, and **their content is not its concern**." §21.6 row: "alignment gaps, the pre-trailer pad, superseded structures | Slack: **unconstrained content, no conformance requirement**, counted and reported by a verifier". And the register (§21.2), whose completeness §21.1 makes normative, has **no row** for a nonzero pad: F10/F11 range only over a *structure* occupying the gap, never over the gap's byte content.
- **Discriminator.** Take Appendix A's exact 128-byte file and set bytes [20, 64) to `AA` ×44. Nothing else changes: the directory CRC covers only [16, 20) and the trailer CRC covers only [64, 124), so both still verify (I recomputed both). Verifier A: **reject-file** (`[R-CNT-05]` violation, per `[R-SEC-04]`/Appendix H). Verifier B: **certifies the file conforming** and reports "44 slack bytes" (`[R-CNT-21]`, `[R-LIF-08]`, §21.6). Opposite verdicts on identical bytes, from a verifier — the actor §2.3 `[R-CNF-11]` defines as the one that "certifies conformance". The same divergence recurs on every alignment gap in an `A`-declared layer.
- **What I searched to refute.** Grepped every occurrence of `R-CNT-03`, `R-CNT-05`, `R-CNT-21`, `R-LIF-08`, `R-SEC-04`, "pre-trailer", "declared padding", "declared-padding", "zero check", "declared gaps". §2.1's normativity carve-out removes Appendices G and H as *authority* but leaves `[R-CNT-05]` and `[R-SEC-04]` as normative text asserting the check. No precedence rule covers this pair: §21.1's "the rule governs" applies only to register rows versus their cited rules, and §21.6's slack row is not a violation row. §10.2/§10.4's registry precedence rule and `[R-EXT-05]` are about identifier spaces, not this. No sentence anywhere reconciles "a verifier MUST treat a violation as a validity error at file scope" with "no conformance requirement rides on slack content either way."
- **Note on the term.** "Declared padding" is used in §5.1 (listed *separately* from "pre-trailer pad" in the same sentence) and §22.3, and is defined nowhere; §5.2's coverage classes contain no such class. `[R-SEC-04]`'s "covered by no checksum" also excludes edge-tile padding (§14.5), which *is* covered by the stored tile's crc — so the phrase can only mean inter-structure slack, which §5.2 says is unconstrained.

### CONTRADICTION

**C1. §21.8's instance total is arithmetically wrong under §21.1's own counting rule.**
- §21.1: "Instances within a cell are separated by semicolons, and a cell reading — is one instance; **the count is therefore mechanical**."
- §21.8 `[R-ERR-02]`: "Every row of §21.2 through §21.5 — 120 conditions over **214 named instances** — has at least one conformance vector … and a row naming instances has one vector per instance."
- Mechanically counted: §21.2 = 69, §21.3 = 81, §21.4 = 43, §21.5 = 20 → **213**, over 120 rows (row count is correct). No consistent rule yields 214: T18's cell ("a second concatenated compressed frame; a skippable frame (magic 0x184D2A5x) before; after; or between frames") mechanically yields 4 while its evident meaning is 2, giving 211; expanding parentheticals instead (L1's "extent_length (layer record and sub-record slots)") reaches 214 only if *no other* parenthetical is expanded, which F5, L22, T15 and T25 contradict. Because `[R-ERR-02]` and §24 `[R-VEC-03]` make the corpus's size a normative function of this count, the number is load-bearing.
- Same rule is further broken by cells that are quantifiers rather than fields: L3 "any layer-record inline-payload field" (1 instance for a condition ranging over ~15 fields), F5 "trailer (**e.g.** version_major/version_minor written as u32 each)" — an "e.g." is not an enumeration.

**C2. §21.6's heading and lead classify two of its own rows as non-violations while the rows state the file is nonconforming.**
- §21.6 heading: "Conditions that are **not violations**"; lead: "These are defined behaviors, **not errors**. A reader that treats any of them as a failure is the nonconforming party."
- Its own rows: "A user-metadata document's object members are not sorted … | **The file is nonconforming**, but the document is readable: a verifier reports it" (`[R-MTA-05]`, whose §18.2 text is "the file is nonconforming, a verifier **MUST** report it"); and "A registered record type's stored MU or PE bit differs … | **The file is nonconforming**" (`[R-CNT-22]`).
- Consequences: (a) §21.1's normative completeness claim ("The register below enumerates every violation this specification names") is broken, since §21.8 scopes the register to §21.2–§21.5 and these two violations live outside it; (b) §2.4 `[R-CNF-07]` ("Every detectable violation … is assigned **exactly one** reader outcome: reject-file, reject-layer, reject-tile, or ignore-record") is broken — both are detectable violations with no assigned outcome, since readers process them unchanged.

**C3. Appendix G asserts a SHOULD is mandatory.**
- Appendix G: "Everything else the profile needs is **already mandatory**: zero declared gaps (`[R-CNT-03]`)…"
- §5.2 `[R-CNT-03]`: "Writers **SHOULD** zero the gaps they create … no conformance requirement rides on slack content either way."
- The profile's stated purpose is byte-identical output. Two writers following every numbered item of Appendix G, one zeroing the pre-trailer pad and one not, both emit conforming files with different bytes — the profile does not close the degree of freedom it claims is already closed. (Appendix H's conforming-*writer* checklist repeats the error: "zeroes the gaps it creates (`[R-CNT-03]`, §5.2)" listed among obligations.)

**C4. F7 cites the wrong governing rule.**
- §21.2 F7: "File size is below the 128-byte minimum … | `[R-CNT-01]` (R-ENC-07, R-CNT-06)".
- The 128-byte minimum is §5.1 `[R-CNT-27]` ("No conforming file is shorter than 128 bytes … A reader MUST treat a shorter file as a validity error at file scope"). `[R-CNT-01]` states only that F equals committed_file_length and is a multiple of 64. Grep confirms `[R-CNT-27]` appears exactly once in the document (line 485) and is cited by no register row — so under §21.1's "where a row and the rule it cites diverge, **the rule governs**", F7 resolves to a rule that does not contain its condition.

### OBSERVATION

**O1. Appendix A is byte-exact.** I rebuilt all 128 bytes from §6.1, §7.1, §6.2 and §9.2 and recomputed both CRCs with an independent CRC-32C implementation: directory `[16,20)` = CRC of zero bytes = `00 00 00 00` ✓; trailer CRC over `[64,124)` = `0xE00938D2`, stored `D2 38 09 E0` ✓; F = 128, multiple of 64 ✓; pad = 44 bytes = 64 − 20, the minimum to the next 64-boundary ✓; dir_offset 16 ≥ 16, dir_length 4 ≥ 4, dir_offset+dir_length = 20 ≤ F−64 = 64 ✓; file_id `0x0123456789ABCDEF` ≠ 0 ✓; annotation table offsets all correct. Appendix B's `0xE3069283`, `0x00000000`, and `0xEECB3BB2` (CRC of 2¹⁶ × `FF×16 00×4`) all reproduce exactly.

**O2. Appendix B and Appendix C agree with their defining sections on every entry.** I checked all 24 Appendix B rows against §4.2, §4.5, §4.6, §5.1, §6.1, §6.2, §6.4, §7.2, §7.4, §11.3, §15.1, §15.2, §15.4, §16.1, §16.2, §17.2, §18.3, §21.9 — no divergence. Appendix C matches §7.3, §12.1, §12.2's pinned-reservation note, §17.2, §17.3, §14.1, §11.4, §15.1, §18.2, §6.3, §18.4 — no divergence. §21.9's derived numbers also check: 2³² entries → 2¹⁶ segments × 4 B = 256 KiB exactly; 2³⁶ → 4 MiB exactly; §24's "tens of gigabytes" for a 2³² index region = 85.9 GB.

**O3. Register omissions against §21.1's normative completeness claim.** Each is a violation the specification names with no row in §21.2–§21.5 (verified by grep):
- **Two top-level user-metadata records.** `[R-CNT-14]`: "at most one file-scope user-metadata record, a second being a validity error at the directory's scope (reject-file)." L18 covers only the layer-sub-record case; §21.2 has no counterpart.
- **Front signature block ≠ the constant 16 bytes.** `[R-CNT-04]` requires a local reader to "verify the full block by byte equality" and reject-file on mismatch. F2 covers only the byte-*reversed* instance (governed by `[R-ENC-02]`); a flipped byte in `[0,8)` or a nonzero reserved half `[8,16)` has no row. `[R-CNT-04]` appears in the register only as a parenthetical on F2.
- **A user-metadata record whose `inline_length` ≠ 1.** `[R-MTA-03]`: "a validity error at the record's containing scope." No row at file or layer scope.
- **A user-metadata extent whose `extent_length` is 1–4.** `[R-CNT-25]`: "one whose extent_length is less than 5 … is a validity error at its containing scope." F26 and L11 cover only the `(0,0)` slot.
- **A standardized metadata key outside its listed scope, or of the wrong shape.** `[R-MTA-07]` makes it a writer MUST NOT with a reader MUST-ignore-the-key. Its outcome — *ignore the key* — is a fifth outcome absent from §2.4's four-way enumeration (`[R-CNF-07]`) and from §21.5.
- **`[R-LIF-02]` step 5's "generation one greater than the prior trailer's"** and `[R-WRT-04]` step 6's "the same file_id". Both are MUSTs on a commit; neither is decidable from the live state (§9.7's note: "Nothing here enumerates prior commits"), neither has a register row, and neither appears in §21.7's "what no check detects", which lists only content incorrectness.

**O4. The register's condition numbering carries unexplained artifacts.** F8/F9 and F34/F35 are verbatim duplicates (identical condition, instances, detector, detection point, rule); F10/F11 are near-duplicates. §21.1 says "each row is **one** malformed condition", and `[R-ERR-02]` demands a vector per row — so the corpus must contain two vectors indistinguishable in every recorded field. §21.3 skips L40 with no note, unlike the explicit withdrawal note §14.4 gives `[R-SER-04]`; the stated "47 conditions" is nonetheless correct (48 labels − 1 gap).

**O5. F1's instance list names a field whose violation is unconstructible.** F1 (reject-file, "detectable only through that field's own value or range gate") lists **file_id**. The only gate on file_id is ≠ 0, and no nonzero file_id has a byte-reversal that reads as 0 — so a big-endian file_id always yields a conforming file, and no vector can have the expected verdict `[R-ERR-02]` demands. (I checked the other five instances: version_major, dir_offset, dir_length and committed_file_length are all detectable; generation is detectable for values whose BE top byte lands ≥ 0x80, e.g. generation 128 → LE 2⁶³, out of `[R-ENC-03]`'s domain.)

**O6. §21.9's minimum guarantees are per-quantity and do not compose, so the acceptance floor is not implementable.** `[R-CNF-03]` and `[R-ERR-03]` jointly oblige a conforming reader to accept any file none of whose values exceeds the table, and `[R-ERR-04]` makes declining such a file nonconforming. A file with 65,536 layers each declaring rank 32 and C = 4096 has every tabled quantity at or below its bound, yet its directory is ≈ 1.9 GB (4096 channel entries × ≥ 7 bytes + 32 dimension entries × 18 bytes ≈ 29 KB per layer record), and §19.1 step 3 plus `[R-CNT-11]` require fetching and CRC-verifying that region **whole** before any other use. §21.9's own note asserts the 65,536-layer guarantee is "roughly a 12.5 MiB directory" — true only at ~200 bytes per layer record, i.e. only when C and d are small. The table bounds no product and no directory size.

**O7. §24's constructibility carve-out is narrower than the obligation it qualifies.** `[R-VEC-03]` requires a vector "at its stated bound" for "every hard limit of `[R-ERR-05]`", and §24 excuses only §21.9's tile-count guarantee. But the `[R-COD-07]` hard limit (codec 4 at decoded tile size `0x7E000000` ≈ 1.97 GiB) exceeds §21.9's 256 MiB decoded-tile guarantee, so a conforming reader MAY decline the bound vector on resource grounds (`[R-ERR-04]`) — the vector cannot discriminate. (I refuted the parallel worry about `[R-ERR-05]`'s 2⁶³−1 offset bound: `[R-VEC-02]` records "whether the file is conforming", so a *nonconforming* vector carrying `offset = 2⁶³−1` in a 128-byte file is constructible and exercises the bound.) Separately, `[R-VEC-03]`'s "every **boundary value**" names no enumerated set, so unlike the register-row clause it is not mechanically checkable.

**O8. §20.4's byte-identity protection lapses exactly where §20.4's own rationale says it matters.** `[R-WRT-05]` binds only records the updater "retains and does not logically modify"; a modified record "is new output under its writer obligations". Every commit that supersedes a tile modifies that layer's record (its extent slot re-points at the new index region), so the record may be re-serialized freely — including re-encoding its name from NFD to NFC under `[R-ENC-14]`'s SHOULD, which `[R-ENC-13]` makes an identity change. §20.4's rationale names precisely this hazard ("a re-serializer that renormalized a name would change the name's identity") and offers byte-identity as the foreclosure, but the foreclosure does not reach modified records. I did not report this as byte-level: §20.1 lists "amending metadata" among an appender's licensed operations, so renaming a layer is permitted and both outputs conform. The term "logically modify" is itself undefined — under a literal reading, a commit that relocates an unchanged layer's index (a trigger §20.3 step 4 explicitly contemplates via "index placement") retains a record it does not *logically* modify while necessarily changing its extent slot, which `[R-WRT-05]` forbids.

**O9. §20.5 omits the layout invariants that §20.2 and §20.3 both state.** `[R-WRT-07]` says a compactor "is free to place structures anywhere **§5.2** admits", and its exhaustive list of permitted layer-record changes is extent slot + `crc_of_crc_array` — clearing `A`/`S`/`A_slab` is not among them. So a compacted layer keeps its declaration while §5.2-only placement can violate `[R-SLB-01]`/`[R-SLB-03]`, making the output nonconforming. `[R-SLB-04]`'s trigger ("supersedes a stored tile in, or grows the extents of") does not fire on relocation, so it does not close the gap either. §20.2 says "every declared layout invariant (`[R-SLB-01]`, `[R-SLB-03]`)" and §20.3 step 4 says "re-established or cleared"; §20.5 says neither. Resolvable — `[R-CNF-05]`/`[R-CNF-06]` require conforming output, so §16 binds — hence an observation, but the parallel structure is broken.

**O10. §19.1 step 4 and §21.5 R1 disagree on what the open walk covers.** R1 (user-metadata encoding byte invalid) has detection point "open (top-level)", but §19.1 step 4 enumerates what the record walk does — MU gate, multiplicity, extent-slot validity for non-layer top-level records, layer names — and does not include parsing a user-metadata record's one-byte inline payload. Outcome is ignore-record either way, so only the timing of the SHOULD-report diverges.

**O11. The local/remote reader split makes an observable verdict follow from implementation technique.** §19.1 step 1 restates §6.1: a local reader MUST reject-file on a front-block mismatch; "a remote reader MAY defer or omit that check." §6.1 defines a local reader as "one whose transport delivers the file's bytes from offset 0 without a separate request." A reader of a local file that opens with positioned reads at [F−64, F) and [dir_offset, …) does issue a separate request for offset 0, so it can classify itself as remote and skip the check — while an mmap-based reader of the same file cannot. Same bytes, opposite verdicts (reject-file vs. read successfully), with the classification turning on I/O strategy, which §2.1's phrasing-discipline note says requirements never constrain. Primary site is §6.1, outside my range; I record it because §19.1 and Appendix A restate it and Appendix H's conforming-reader checklist omits the front-block check entirely.

**O12. Cross-range leftover from the same retired concept as the byte-level finding.** §9.6 `[R-LIF-06]`: "Generation enumeration **for coverage verification (§5.2)** is the same probe continued to offset 0" — while §9.7 `[R-LIF-08]` says the verifier "walks the live state only" and its note says "Nothing here enumerates prior commits." Outside §19–§24, flagged only because it is the same pre-live-state-coverage residue as `[R-SEC-04]`, Appendix G's "zero declared gaps", Appendix H's "declared-padding content", and §5.1's undefined "declared padding".

## Findings

### BYTE-LEVEL AMBIGUITY

**None found.** Every candidate above is resolved by an explicit sentence, and the document's four meta-rules do most of the work: §21.1 ("where a row and the rule it cites diverge, the rule governs"), `[R-CNF-02]` (conduct binds the actor, the predicate binds the bytes), §2.4 `[R-CNF-08]` (owning scope), and §21.6 (defined non-violations).

### CONTRADICTION

**CON-1 — "Declared padding" and the verifier's zero check.** §22.3 `[R-SEC-04]` (line 2801): *"Declared padding is covered by no checksum (§8.1): corruption confined to padding is invisible to a reader and caught only by a verifier's zero check (`[R-CNT-03]`)."* But `[R-CNT-03]` (§5.2) is a SHOULD that ends *"no conformance requirement rides on slack content either way"*, `[R-CNT-21]` says slack's *"content is unconstrained, and no conformance requirement applies to it"*, and §21.6 lists "the pre-trailer pad" under **conditions that are not violations**. Reinforcing the stale side: §5.1 (line 475) still lists "declared padding" among the structures between front block and trailer, though §5.2's coverage classes no longer contain it; Appendix H (line 3218) lists "declared-padding content (§5.2)" as a verifier obligation §5.2 does not state; and `[R-LIF-02]` step 5 and `[R-CNT-05]` say "the **zero** pad" / "the **zero** pre-trailer pad" in MUST clauses.
*Discriminator (would be byte-level if unresolvable):* Appendix A's 128-byte file with byte 20 changed from `00` to `01`. Every checksum still verifies (the pad lies outside `[16,20)` and outside `[F−64, F−4)`). Verifier A certifies; Verifier B reports a file-scope validity error.
*Searched:* `declared padding`, `declared-padding`, `zero pad`, `zero pre-trailer`, `zero check`, `pre-trailer pad`, all 27 occurrences of `slack`, and the whole of §21.6.
*My judgment:* resolvable toward "conforming" — `[R-CNT-03]`/`[R-CNT-21]` answer the exact question in as many words, §21.6 names the pad, and §22.3 self-refutes by attributing the check to a requirement that has none. Hence not counted as byte-level. **The three stale sites should be deleted.**

**CON-2 — Does coverage verification enumerate generations?** §9.6 `[R-LIF-06]`: *"Generation enumeration for coverage verification (§5.2) is the same probe continued to offset 0."* §9.7's note: *"Nothing here enumerates prior commits. A verifier certifies what a reader can reach and counts what it cannot, which is decidable from the live trailer in one pass and does not depend on reconstructing the file's history."* And `[R-LIF-08]`: *"A verifier checking `[R-CNT-02]`'s partition walks the live state only."* One sentence assigns backward probing a role in coverage verification; the other two deny that role exists. No byte consequence — §5.2's definition of slack fixes the number either way — but the §9.6 sentence is post-ADR-0048 residue.
*Searched:* `certif`, `slack`, §5.2, §9.6, §9.7, §22.3.

**CON-3 — `[R-ERR-02]`'s instance count is wrong.** §21.8: *"Every row of §21.2 through §21.5 — 120 conditions over **214** named instances."* §21.1 fixes the counting rule: *"Instances within a cell are separated by semicolons, and a cell reading — is one instance; the count is therefore mechanical."* Applying exactly that rule to the four tables gives **213** (F 37 rows/69 instances, L 47/81, T 26/43, R 10/20). The row count 120 is right; the instance count is off by one. This is normative: `[R-ERR-02]` obliges the corpus to carry one vector per instance, and `[R-VEC-03]` inherits it.
*Searched:* mechanically parsed every register row (49 cells read `—`, 71 name instances; no empty cells).

**CON-4 — Byte-identical re-emission vs. writer conformance.** §20.4 `[R-WRT-05]`: an updater *"MUST re-emit byte-identically — header, inline payload, and extent slot — every record it retains and does not logically modify"*. §7.2 `[R-CNT-12]`: *"Writers MUST NOT emit the combination MU = 1 with PE = 0"* (likewise nonzero reserved flag bits), and §2.3 `[R-CNF-06]`: an updater *"MUST satisfy every writer requirement for the bytes it produces"*. For a retained record carrying those bits, the two MUSTs cannot both be obeyed, and no priority is stated.
*Discriminator:* file whose layer record for layer `a` carries `flags = 0x0001` (L47: verifier-detected, so an updater's reader-level obligations never trip on it). An updater commits a change to layer `b`. Updater A re-emits `01 00` at the record's flags field; Updater B repairs it to `03 00`. Outputs differ in that byte, in the directory's terminal CRC-32C, and in the trailer CRC — 9 bytes.
*Searched:* `byte-identical`, `re-emit`, `[R-CNT-22]`, `[R-WRT-08]`'s table, `[R-CNF-05]`, `[R-CNF-06]`, `[R-CNF-12]`.
*Why not byte-level:* the conflict is reachable only from a nonconforming input, and `[R-CNF-12]` withdraws every obligation for such files. A one-clause fix ("an updater MUST NOT propagate a stored-flag defect; correcting it is not a logical modification") would close it.

### OBSERVATION

**OBS-1 — Three duplicated register rows.** F8 ≡ F9 and F34 ≡ F35 are byte-identical rows (condition, instances, detector, detection point, rule); F10 and F11 differ only in a clause about the pad and state the same condition. So §21.2's "37 conditions" and §21.8's "120 conditions" count 117 distinct conditions. `[R-ERR-02]` demands a vector per row, so the corpus is asked for three redundant vectors and for 14 duplicate instance-vectors (F34/F35 name 7 instances each).

**OBS-2 — Row L40 is missing with no note.** §21.3 runs L1–L48 skipping L40; the stated count (47) matches, so the omission is deliberate, but §2.2's retirement rule covers *requirement identifiers*, not register rows, and §14.4 shows the document's own convention for announcing a retirement (`[R-SER-04]`'s explicit note). A reader auditing coverage cannot tell whether L40 was withdrawn or lost.

**OBS-3 — Register completeness gaps (§21.1 calls these defects in the document).** Violations this specification names that have no row: (a) a second file-scope user-metadata record, `[R-CNT-14]`, reject-file — the layer-scope twin exists as L18; (b) a user-metadata record with `extent_length` in 1–4, `[R-CNT-25]`, error at containing scope — only the `(0,0)` case has rows (F26, L11); (c) a top-level or sub-record type in the **reserved** range, which `[R-CNT-15]` makes a verifier-detected validity error — F36 covers only MU = 1, and R10 covers unknown MU = 0 as ignore-record; (d) `[R-MTA-09]`'s and `[R-COD-11]`'s "MUST NOT certify"; (e) a nonconforming file under `[R-CNT-22]` (stored-flag mismatch on a registered type) is only SHOULD-reported. Also, R10 appears simultaneously in §21.5 (a table §21.1 introduces as enumerating *violations*) and in §21.6 (*conditions that are not violations*).

**OBS-4 — The slack total has no closed form, and §9.7's walk list omits two live-state members.** `[R-CNT-21]` makes reporting it a verifier MUST, but no formula is given. §9.7 `[R-LIF-08]` says *"Bytes the walk does not reach are slack"* and describes a walk over the directory, record extents, index regions and non-sentinel entries, each required to lie *"within [16, F − 64)"* — a range that excludes the front signature block and the trailer, both of which §5.2 places **in** the live committed state. Applied to Appendix A's file, three defensible totals exist: 44 (§5.2, correct), 60 (trailer counted as the walk's origin, front block not), 124 (literal §9.7). Suggested fix: state the formula, e.g. slack = F − 16 − 64 − Σ|walked structures|.

**OBS-5 — Dangling cross-reference.** §17.4 `[R-COD-11]`: *"the rule of §9.7(d) applied to content"*. §9.7 is unlettered prose with no items (a)–(d).

**OBS-6 — `[R-CNT-19]` is false for ancillary extents.** §8.1: *"Every field of every structure is covered by exactly one checksum"*, excepting only the front block and the map's terminal checksum fields. The map has six rows; an unknown/ancillary record's extent (§5.2 admits it as a coverage class, "whatever the record's type") appears in none of them, so those bytes are live committed state under no checksum at all — and §9.7's walk asks the verifier to check "that each verifies against the checksum covering it", which for such an extent does not exist.

**OBS-7 — Certification is not a pure function of bytes, in three places the document does not flag.** `[R-CNF-02]` makes *file conformance* byte-pure, but: (a) `[R-MTA-09]` lets each verifier pick its own user-metadata decode bound (≥ 16 MiB) and forbids certifying a document it declines to decode — so a conforming file with a 20 MiB document is certified by one verifier and not by another; (b) `[R-COD-11]` does the same for codec/filter executability; (c) a conforming file carrying an experimental-range record type with MU = 1 at file scope must be *rejected* by every conforming reader (`[R-CNT-15]`), hence by every verifier, though `[R-CNT-15]` itself calls the file conforming. §21.6's closing paragraph makes exactly this distinction for an unimplemented `version_major` ("The outcome records a reader's capability, not a defect in the bytes") but nowhere else; the same paragraph should cover (a)–(c).

**OBS-8 — Slack can be resurrected, and only a §9.6-style backward probe could see it.** Nothing forbids a commit from pointing a new index entry at a byte range an earlier generation wrote and a later one superseded (committed bytes are immutable, so the writer *writes* nothing there; `[R-LIF-02]` step 1's "begin writing at exactly F" is not violated). The file is conforming and the classification is unambiguous under §5.2's leading clause. Worth a note, since it means "which commit wrote these bytes" is not merely undecidable from the live state (§5.2's rationale) but genuinely not well defined.

**OBS-9 — Terminology overload.** §6.3 `[R-CNT-24]`: *"The format-major-1 trailer has zero slack: every byte is assigned."* "Slack" is a defined file-level term in §5.2 (`[R-CNT-21]`); using it for unassigned trailer bytes invites misreading, particularly next to a rule about what future majors may redefine.

**OBS-10 — Positive result.** Every constant, worked example, and hex dump I checked is correct: the four CRC-32C values, Appendix A's 128 bytes against its annotation table, §15.4's segmentation arithmetic (16 segments, 16,960 trailing entries, byte offsets 19,660,800 / 20,000,000 / 20,000,064, 1.25 MiB per full segment), §11.4's ordinals (s = 10, in-tile 11,452, disk 74), §14.2's strides and offsets, §14.3's `55 01` / `55 FD`, §17.3's shuffle output, §12.3's 12-byte channel entry, §20.3's 644-byte index region, and §21.9's note (256 KiB at 2³², 4 MiB at 2³⁶).

--- 0. What the reader is ---

Per §2.3 `[R-CNF-03]` there is no subset profile. The reader implements all thirteen sample types (§12.1 `[R-TYP-01]`), all four codecs — none/deflate/zstd/lz4 (§17.2 `[R-COD-03]`), both filters — none/byte-shuffle (§17.3 `[R-COD-09]`), and both channel layouts (§14.1 `[R-SER-06]`). It never offers a flag that disables verification (§8.2 `[R-CNT-20]`: "Verification is not optional: no in-file flag disables it"). It never heuristically repairs (§2.3 `[R-CNF-04]`).

Two transport-shaped variants share one core: a *range source* abstraction with `size()` and `read(offset, len)`, plus a `charges_per_range` bit that decides only speculation policy and the front-block question of §6.1 `[R-CNT-04]` (Finding 1).

--- 1. The open path, byte range by byte range (§19.1 `[R-RDR-01]`) ---

Step 1 — file size. F must be transport-authoritative (§6.4 `[R-CNT-10]`): "a full-response content length, the complete length of a range response, or a size probe"; the reader "MUST NOT substitute the trailer's committed_file_length for the transport size". For a local file this is fstat. For HTTP it is the `/total` term of the 206 Content-Range on the suffix request, so steps 1 and 2 cost one request between them (§6.4).

Step 2 — trailer. Fetch **[F−64, F)**, exactly 64 bytes. Validate in §6.2 `[R-CNT-06]`'s mandated order:
  (i) magic == `8A 4E 52 41 54 0D 0A 1A` at trailer offset 0. This is a comparison against a constant, which §4.5 `[R-ENC-10]` explicitly exempts from the check-before-act rule ("comparing a field against a constant for validation is not acting on it").
  (ii) CRC-32C over trailer bytes [0,60) == the u32 at [60,64).
  (iii) version gate (§6.3 `[R-CNT-07]`): version_major == 0 → reject-file; version_major != 1 → reject-file with a diagnostic distinct from "not a TARN file" and from "corrupt". version_minor is never a rejection reason.
  Only (i)–(iii) touch fields whose positions are fixed across all majors (`[R-CNT-24]`), which is why they come first — a major-2 file must be diagnosed as a major-2 file, not as corruption, and only these three fields are guaranteed to mean the same thing there.
  Then, gates passed, before acting on any of them: incompat lane flags bits 0–15 all clear (any set bit → reject-file, `[R-CNT-08]`); ignore lane bits 16–31 ignored entirely; committed_file_length == F and F mod 64 == 0; dir_offset ≥ 16; dir_length ≥ 4; dir_offset + dir_length ≤ F − 64 (computed in 128-bit or with an overflow guard, `[R-ENC-04]`); generation ≥ 1; file_id != 0; reserved bytes [56,60) all zero. Any failure: reject-file.
  Also here: F < 128 → reject-file (`[R-CNT-27]`). I check this before issuing the suffix read, since a 40-byte file has no [F−64,F).
  This trailer is the session snapshot (§9.5 `[R-LIF-05]`). No later step re-reads the file's end. If the tail is not a valid trailer the file is torn and the reader **MUST NOT scan backward** (`[R-LIF-05]`); backward scanning is a recovery-tool operation only (§9.6 `[R-LIF-06]`), and my reader does not implement it.
  Local reader only: verify bytes **[0,16)** by byte equality against `89 54 41 52 4E 0D 0A 1A` + 8 zero bytes (§6.1 `[R-CNT-04]`); mismatch → reject-file. See Finding 1 for how I decide who does this.

Step 3 — directory. Fetch **[dir_offset, dir_offset + dir_length)**. Verify CRC-32C over the first dir_length − 4 bytes against the final 4 (§7.1 `[R-CNT-11]`); mismatch → reject-file, *before any other use of the region*. The directory is always raw — "no codec involvement on the open path" (§7.1).

Step 4 — record walk, entirely over resident, CRC-verified bytes. The record sequence is the first dir_length − 4 bytes. Parse 24-byte headers (§7.2 `[R-CNT-12]`): type u16, flags u16, inline_length u32, extent_offset u64, extent_length u64, then inline_length bytes. Must parse to zero residue; a header or payload past the sequence end → reject-file (F32). Type 0 → reject-file (F27). For unknown types: MU (bit 0) = 1 → reject-file; MU = 0 → ignore-record (`[R-CNT-15]`). Multiplicity: any number of layer records including zero; at most one top-level user-metadata record, a second → reject-file (`[R-CNT-14]`, F37). Extent slots on non-layer top-level records: (0,0) is "no extent"; exactly one half zero, or offset in 1–15, or offset+length > F−64, or an overflowing sum → reject-file (`[R-CNT-13]`, F33/F34/F35). A top-level user-metadata record additionally requires inline_length == 1 (§18.2 `[R-MTA-03]`, F26 → reject-file), a non-(0,0) extent (F24), and extent_length ≥ 5 (F25) — note these three are *reject-file* while everything about the document those bytes hold is *ignore-record*; the quarantine begins after the slot, not at it (§18.1 `[R-MTA-02]`: "that failure precedes the document").
  Then build the layer table: for each type-0x0001 record, read its inline payload's leading name (u8 length prefix + bytes) and check §4.6's name rules (`[R-ENC-12]`); duplicates across layers → reject-file at open (`[R-ENC-15]`, F6). See Finding 4 for the ordering question here.

**That is the whole open.** §19.1: "It consumes the trailer and directory only — no extent slot's content, no tile index, no payload". Its working set is invariant in F and in layer count.

Speculation (§6.4 `[R-CNT-09]`): a remote reader may issue one suffix request of min(65536, F) instead, and if the returned buffer contains [dir_offset, dir_offset+dir_length) skip request 2 — "Writers SHOULD keep dir_length plus the pre-trailer pad plus 64 within 65,536 bytes". A 200 response to a range request must be handled deliberately, never by treating the body prefix as the requested range (`[R-CNT-10]`); my reader aborts the body and falls back to size-probe + absolute range.

--- 2. Validation tiers, and why they are ordered this way (§19.2 `[R-RDR-02]`) ---

The rule fixes the *latest* legal detection point, per structure, at "the reader's first reliance on the structure that carries it". Four tiers:
  T1 **open** — front block (local), trailer, directory region, record walk, layer-name namespace.
  T2 **layer access** — the full layer record (§19.3), before any use of that layer's declarations.
  T3 **tile use** — index chain, entry classification, payload CRC, decode, before any sample of that tile is returned.
  T4 **extent use** — a record extent's CRC and the content rules of the document it carries, before anything the extent holds is returned.
Plus a fifth, outside the reader tiers entirely: **certification**, the rows §21 assigns to a verifier, which "imposes no reader obligation".

Why this order: it is dependency order over the chain of trust of §8.2 — "trailer → directory → (per layer) crc_of_crc_array → segment CRC array → index segment → index entry → stored tile" — combined with `[R-ENC-05]`'s absolute prohibition ("MUST NOT allocate, seek, or issue I/O based on any integer obtained from a file before the checksum covering it has been verified"). Each tier's inputs are exactly the outputs of the previous tier's verified structure, so no tier can be reordered without acting on unverified integers. The second reason is cost isolation: because T2 and T3 are per-layer and per-tile, "a violating record in a layer never accessed leaves every other layer's reads conforming", and the open stays two requests at any layer count. The third is determinism of the served-versus-failed boundary — §19.2's Rationale: "no conforming reader returns data its tier's validation would have refused", while earlier detection stays licensed (`[R-CNF-12]`), so divergence between conforming readers runs only toward earlier rejection, never toward silent acceptance.

Failure at any tier takes the violated rule's own scope, not the tier's. The load-bearing case: an index-chain CRC failure is *detected* at tile use but is *scoped* to the layer (`[R-IDX-04]`, register L38/L39).

--- 3. Layer access (§19.3 `[R-RDR-03]`) ---

Performs **no I/O**. Everything is decidable from the resident directory plus F. On first touch of a layer, validate in this order (all failures reject-layer unless noted):
  extent slot rules (`[R-CNT-13]`): (0,0) iff entry_count == 0, else offset ≥ 16 and offset+length ≤ F−64 (L16/L17/L18);
  exact parse of the inline payload in §7.4's field order with no padding: name; layout u8; linearization u16; codec u16; filter u16; A u64; S u64; A_slab u64; d u8; C u16; d dimension entries (name, E u64, T u64); C channel entries (name, type u16, fill u8len+bytes); index_encoding u8; entry_count u64; crc_of_crc_array u32; then sub-records to the end with no residue (`[R-CNT-18]`, L24/L15);
  sub-record walk: type 0 → reject-layer (L14); unknown type MU=1 → reject-**layer**, never reject-file (L25); MU=0 → ignore-record; a type-0x0001 record nested here → reject-layer (L27); at most one user-metadata sub-record (L20); user-metadata sub-record needs inline_length 1, non-(0,0) extent, extent_length ≥ 5 (L13/L11/L12);
  names: dimension and channel names per §4.6, unique within the layer (L5/L8/L9/L10);
  value sets: layout ∈ {1,2} (L37); linearization == 1 (L34); codec ∈ {1..4} (L44); filter ∈ {1,2} (L46); index_encoding == 1 (L32); every channel type ∈ {1..13} (L35) — and never infer an element size for an unassigned type value "whatever pattern its bits suggest" (`[R-TYP-03]`);
  fill: each channel's fill byte length == its type's element size (L31); a bool fill byte ∈ {0x00, 0x01} (L36);
  geometry floor: d ≥ 1, C ≥ 1, every Tᵢ ≥ 1, every Eᵢ ≥ 0 (L33); Eᵢ = 0 is *valid* and yields an empty layer (`[R-GEO-02]`);
  layout declarations: A ≠ 0 and S ≠ 0 together → reject-layer (`[R-CNT-16]`, L21); A nonzero must be a power of two 512 ≤ A ≤ 2^62 (L40); A_slab must be 0 when S = 0 (L29) and a power of two 1 ≤ A_slab ≤ 2^62 when S ≠ 0 (L30);
  codec bound: codec 4 with decoded size > 0x7E000000 → reject-layer (`[R-COD-07]`, L45) — see Finding 2 for the planar case;
  arithmetic, all overflow-checked against 2^63 − 1 (`[R-ENC-04]`, L1/L2): Gᵢ = ⌈Eᵢ/Tᵢ⌉ computed as Eᵢ/Tᵢ + (Eᵢ mod Tᵢ ≠ 0), *never* as (Eᵢ+Tᵢ−1)/Tᵢ (§11.2's Note — the naive idiom's intermediate sum leaves the declared domain); N = ∏Gᵢ; P = ∏Tᵢ; addressed-tile count = N interleaved, C·N planar; Q = ΣBᵢ; decoded sizes P·Q / P·Bᶜ / ⌈P/8⌉;
  index cross-checks (`[R-CNT-17]`, L22/L23): entry_count == addressed-tile count, and extent_length == entry_count×20 + ⌈entry_count/2^16⌉×4 (0 when entry_count is 0); crc_of_crc_array == 0 when entry_count == 0 (L28).
Only then is the layer usable, and only then does the reader allocate anything sized from its declarations.

--- 4. The tile-read algorithm (§19.4 `[R-RDR-04]`) ---

Given a coordinate (or region) and a channel set on an accessed layer:

**(1) Domain.** Point request: 0 ≤ xᵢ < Eᵢ for every i, else the *request* fails "with no verdict on the file" (`[R-MDL-01]`) — this is not a validity error and must not be reported as one (§21.6). Region request: intersect with the extents; a disjoint region, or any region of a zero-extent layer, succeeds and returns no samples (`[R-GEO-02]`).

**(2) Ordinals.** tᵢ = xᵢ div Tᵢ, uᵢ = xᵢ mod Tᵢ. In-tile ordinal = Σ uᵢ·∏_{j>i} Tⱼ — row-major "for every linearization value, permanently" (§11.4), never affected by the linearization field. Spatial ordinal s = Σ tᵢ·∏_{j>i} Gⱼ under linearization 1. Disk ordinal = s (interleaved), or c·N + s per requested channel c (planar, channel-major). Empty product is 1, so d = 1 reduces to u₀ and t₀.

**(3) Index chain**, per needed entry, cached per §15.4's Note ("'To use' obliges verification, not re-verification"; caching keyed as §9.3 `[R-LIF-03]` licenses, since committed bytes are immutable):
   fetch the **whole** segment-CRC array: ⌈entry_count/2^16⌉ × 4 bytes at region offset entry_count×20; verify against crc_of_crc_array from the layer record;
   fetch the segment containing entry k, segment index σ = k div 2^16, covering entries [σ·2^16, min((σ+1)·2^16, entry_count)) at region offset σ·2^16·20, length (end−start)×20; verify against the σ-th u32 of the array.
   These two ranges "are computable from the layer record alone and MAY be fetched in parallel" (`[R-IDX-04]`); my reader issues them concurrently. Any mismatch → **reject-layer**. Never match a computed CRC against the all-sentinel constant 0xEECB3BB2 — `[R-IDX-05]`: "Equality with the constant licenses nothing for readers: verification is byte comparison of computed CRCs, never constant matching." (Writers may *emit* it for a full all-sentinel segment; a partial segment's CRC must be computed.)

**(4) Entry classification** (§15.3 `[R-IDX-03]`), reading the 20 bytes at region offset 20·k:
   offset == S ∧ length == S ∧ crc == 0 → **valid sentinel**;
   offset == S ∧ length == S ∧ crc != 0 → reject-tile (T6);
   exactly one of offset/length == S → reject-tile (T7);
   non-sentinel with length == 0 → reject-tile (T10: "absence is spelled sentinel; no codec emits zero bytes");
   non-sentinel with offset < 16 → reject-tile (T8);
   non-sentinel with offset > 2^63−1 or length > 2^63−1 → reject-tile (T11);
   offset + length overflowing 2^63−1, or > F − 64 → reject-tile (T9/T12).
   `[R-ENC-03]`/`[R-ENC-04]`'s domain and sum rules apply to non-sentinel entries only — the sentinel is "a reserved pattern, not offsets or lengths" (`[R-IDX-02]`).
   The three *verifier* rows in §15.3's table (intra-layer overlap → reject-layer; cross-scope overlap → reject-file; alignment/slab invariant violated → reject-layer) impose no reader obligation; they need whole-index or whole-file knowledge.

**(4a) THE UNSTORED-TILE PATH.** A valid sentinel short-circuits steps 5 and 6 with **zero payload I/O**. Every requested position of that tile inside the extents returns fill: in a planar layer, exactly that entry's channel's recorded fill; in an interleaved layer, each carried channel's fill in declared channel order, yielding the full fill sample (§13.3 `[R-TYP-08]`). Fill comes from the channel entry and nowhere else — "MUST NOT substitute a type-derived default or any other value, and MUST return fill bit-exactly as recorded" (`[R-TYP-06]`). Crucially, `[R-TYP-09]`: "Fill is produced by exactly one condition: a sentinel entry read from a verified index chain." A malformed entry, a failed CRC array, a failed segment, or failed stored bytes must **never** yield fill (`[R-CNF-09]`: "a read of a rejected tile MUST NOT silently return fill"). Note the cost asymmetry: the sentinel path skips the payload but not the index — the segment still had to be fetched and verified in step 3, so an all-sparse layer still pays the full index cost per segment touched.

**(5) Payload.** Fetch [offset, offset+length) and verify CRC-32C over exactly those stored bytes against the entry's crc field **before decoding** (§8.1, `[R-CNT-20]`); mismatch → reject-tile (T1).

**(6) Decode**, reversing §17.1's two stages: codec first, then the filter's inverse.
   Codec 1: stored bytes are the filtered image verbatim, and `[R-COD-04]` requires length == decoded size — checkable before the payload fetch, so my reader checks it at step 4 and skips the fetch on mismatch (T14).
   Codec 2: exactly one raw RFC 1951 DEFLATE stream — no zlib and no gzip wrapper (T15), no second stream after BFINAL (T16).
   Codec 3: exactly one RFC 8878 frame beginning `28 B5 2F FD` (T17); no skippable frame anywhere and no second frame (T18) — and per §17.2's Note, a whole-buffer decoder does not enforce this by itself, so I confirm the single frame spans the full stored extent via a frame-boundary query; Dictionary_ID must be zero (T19); Content_Checksum_flag must be clear (T20); declared window size must not exceed the decoded size (T21, see Finding 3); Frame_Content_Size, if present, must equal the decoded size (T22) and **must never size an allocation** (`[R-COD-06]`).
   Codec 4: exactly one raw LZ4 block per the pinned Block Format v1.0, decoded with the stored length as input size and the decoded size as output capacity; an LZ4 *frame* (`04 22 4D 18`) is reject-tile (T23).
   For every codec: output length exactly the decoded size, input consumed exactly, no trailing bytes (`[R-COD-08]`, T24/T25).
   Filter inverse (byte-shuffle, `[R-COD-10]`): stride s = the channel's element size for a planar numeric tile, Q for an interleaved tile, and 1 (identity) for a packed bool plane. With n = L/s, restore byte at i·n+j to offset j·s+i.
   Decoded length != decoded size → reject-tile (`[R-SER-07]`, T3). **All allocation is sized from declarations, never from payload content or any embedded size field** — this is §22.2's decompression-bomb defense (`[R-SEC-02]`).

**(7) Extract.** Interleaved: channel c's value at in-tile ordinal u sits at byte u·Q + Fᶜ, Fᶜ = Σ_{j<c} Bⱼ. Planar numeric: byte u·Bᶜ. Planar bool: bit u mod 8 of byte u div 8, LSB-first (§14.3). Padding positions are never returned (`[R-GEO-04]`); pad bits never encode values.

**(8) Return.** Bit patterns unaltered — NaN payloads preserved, −0.0 distinct from +0.0, no canonicalization (`[R-MDL-02]`, `[R-TYP-04]`). The single exception is the one byte a conforming file cannot contain: a nonconforming interleaved bool byte outside {0x00, 0x01}, for which `[R-SER-08]` fixes the charitable path — 0x00 is false, every other byte is true — for a reader that neither detects nor rejects it.

Region reads are this algorithm per covered tile. Payload fetches of ordinal-adjacent stored tiles may be coalesced, but "coalescing is always driven by the entries' explicit offsets and lengths" (§19.4's Note) — a slab declaration guarantees contiguity only within one run, and across runs and planar channel blocks placement is unconstrained (`[R-SLB-05]`). Alignment and slabs are reader-invisible: "offsets are always explicit" (`[R-SLB-01]`).

--- 5. Every degradation path ---

**reject-file** — the file is unusable, nothing in it may be relied on (§2.4). Triggered by: any trailer gate (magic, CRC, version_major 0 or unimplemented, incompat flag bit, size/alignment/bounds/generation/file_id/reserved); F < 128; the directory CRC; a directory-sequence framing failure; type 0; an unknown top-level type with MU = 1; a duplicate layer name; the second top-level user-metadata record; a bad extent slot on a non-layer top-level record; the front-block equality check for a local reader. Served afterward: nothing.

**reject-layer** — that layer's data and metadata are unusable; every other layer is unaffected, and the reader may still list the layer, including its name (§2.4). Triggered by: any §19.3 validation failure; a reserved/experimental/invalid value in layout, linearization, codec, filter, index_encoding, or a channel type; a bad bool fill; a fill length mismatch; geometry-floor or overflow failures; the A/S mutual-exclusion; index cross-check failures; crc_of_crc_array or any segment CRC. Served afterward: every other layer in full, and the layer's own name.

**reject-tile** — that tile's read reports failure; neighbors in the same layer are unaffected (§2.4). Triggered by: any malformed entry classification; a payload CRC mismatch; any codec-level violation or malformed stream; a decoded-size mismatch; codec 1 length mismatch. Served afterward: every other tile of the same layer, including sentinels. **Never** fill in place of the rejected tile.

**ignore-record** — the record is skipped as though absent, decoding of all stored data unaffected, and the loss SHOULD be reported (§8.2, §21.5). Triggered by: an unknown record type with MU = 0 (top-level or sub-record); and *every* way a user-metadata **document** can be unreadable, whatever the containing scope, under `[R-CNT-25]`'s quarantine — encoding 0/reserved/experimental/unimplemented; the extent CRC; a zstd frame-constraint breach; a decode failure; not well-formed JSON or a non-object top level; a leading U+FEFF; a non-finite number or the bare tokens NaN/Infinity/-Infinity; a duplicate key by decoded-string identity; ill-formed UTF-8 including after `\uXXXX` escape resolution (unpaired surrogates); an empty key, a key with U+0000–U+001F, or a key over 255 bytes. Served afterward: everything else in the file, unchanged. Note that unsorted object members are *not* here — the document stays readable and readers process it unchanged (`[R-MTA-05]`).

**Request failure with no verdict on the file** — a point coordinate outside the extents (§21.6). A region request instead succeeds with the intersection, possibly empty.

**Resource refusal, reported as a limit and never as corruption** (`[R-ERR-04]`) — the reader MUST accept any conforming file within §21.9's minimum guarantees (rank 32; C 4096; entry_count 2^32; 65,536 layers; 256 MiB decoded tile; 16 MiB metadata document; 8 MiB zstd Window_Size), and may decline beyond them "at the whole file, or at the narrowest scope whose declarations exceed what it can serve, a layer or a tile". My reader declines at the narrowest scope and tags the failure `RESOURCE_LIMIT`, distinct from every validity error, because "a reader that reports 'too large' as 'corrupt' invites the deletion of intact data".

**Refusals that are not defects in the bytes** (§21.6) — an unimplemented version_major, and an experimental-range record type carrying MU = 1. Both are reject-file, both files may be perfectly conforming, and both get their own diagnostic distinct from corruption.

**Verifier-only conditions** — coverage/overlap, slack totals, alignment and slab invariants, record flag bits (reserved bits, MU=1 with PE=0, a registered type's stored bits), padding content, pad bits, interleaved bool bytes, mis-strided filters, unsorted metadata members, reserved-range type values. These impose no reader obligation (§19.2). My reader implements them behind an explicit `--verify` mode; `[R-CNF-12]` licenses rejecting a nonconforming file on detecting any of them, so the flag changes only strictness, never what is served under it.

**Never implemented in the reader**: the backward recovery scan (§9.6 is "not a reader behavior", `[R-LIF-05]`), and any interpretation of slack (`[R-CNT-21]`).

--- 6. Byte-exact cold remote open at two very different file sizes ---

The invariant first: an exact-range cold open fetches **64 + dir_length bytes in 2 requests**, at any F and any layer count (§19.1 `[R-RDR-01]`, §6.4 `[R-CNT-09]`). dir_length is a function of the *layer count and name/dimension/channel widths*, never of F. Layer-record inline size = (1+|name|) + 34 fixed (layout 1, linearization 2, codec 2, filter 2, A 8, S 8, A_slab 8, d 1, C 2) + Σ_dims (1+|name|+16) + Σ_chans (1+|name|+2+1+elemsize) + 13 trailing (index_encoding 1, entry_count 8, crc_of_crc_array 4) + sub-records; record = 24 + inline; dir_length = 4 + Σ records.

**File S — the 128-byte minimal file (Appendix A, byte-exact in the document).** dir_offset = 16, dir_length = 4, F = 128.
  Request 1: suffix 64 → bytes [64, 128), **64 bytes**; the response also carries F = 128.
  Request 2: [16, 20), **4 bytes** (the empty record sequence's terminal CRC, `00 00 00 00` = CRC-32C of zero bytes).
  **Total: 68 bytes, 2 requests.** Local reader adds bytes [0,16) — 16 bytes, 0 extra requests. Speculative variant: one suffix request of min(65536, 128) returns the entire 128-byte file — **128 bytes, 1 request** — and the front-block check comes free.
  I also costed a small file *with* data: one layer "thumb", interleaved, rank 2, extents (64,64), tile extents (32,32), G = (2,2), N = 4, P = 1024, three uint8 channels r/g/b (Q = 3, decoded tile 3072 bytes), entry_count 4, index region 4×20+4 = 84 bytes. Layer inline 107, record 131, dir_length 135 → open = **64 + 135 = 199 bytes, 2 requests**; and since the whole file is a few KiB, one 64 KiB speculative suffix opens it *and* pre-loads its index and every tile in **1 request**.

**File L — a 4 TiB file (F = 4,398,046,511,104 = 2^42, a multiple of 64), three layers plus one file-scope user-metadata record.**
  "reflectance": interleaved, dims y/x extents (131072, 131072), tile extents (512,512) → G = (256,256), N = 65,536, P = 262,144; four uint16 channels b1..b4, Q = 8, decoded tile 2,097,152 bytes; entry_count 65,536 → 1 segment, index region 1,310,724 bytes; one user-metadata sub-record. Inline 152, record 176.
  "elevation": planar, tile extents (256,256) → G = (512,512), N = 262,144, P = 65,536; one float32 channel, decoded tile 262,144 bytes; entry_count 262,144 → 4 segments, index region 5,242,896 bytes. Inline 102, record 126.
  "mask": planar, same grid; one bool channel, decoded tile ⌈65536/8⌉ = 8,192 bytes; entry_count 262,144 → 4 segments, index region 5,242,896 bytes. Inline 94, record 118.
  File-scope user-metadata record: 24 + 1 = 25.
  Record sequence 445 bytes; **dir_length = 449**.
  Request 1: suffix 64 → **64 bytes**. Request 2: [dir_offset, dir_offset+449) → **449 bytes**. **Total: 513 bytes, 2 requests.**
  Speculative variant: one 65,536-byte suffix window captures trailer, pad and directory together (449 + pad + 64 ≪ 65,536, exactly what `[R-CNT-09]` asks writers to arrange) → **65,536 bytes, 1 request**.

**The comparison.** File L is 34,359,738,368× the size of File S and costs 7.5× the open bytes (513 vs 68) — and that factor is entirely the three layer records; it would be identical if the file were 40 GB or 40 PB. This is the §6.4 invariant made concrete: "What the open does bind is its *working set*: the trailer and the directory, and nothing else, at any file size and layer count."

**What is *not* flat — the first cold tile read** (§19.4 steps 3–5, §1's "reading one tile costs that layer's segment-CRC array, the index segment covering the tile, and the tile's own bytes"):
  File S' ("thumb", entry_count 4): CRC array 4 bytes at region offset 80 + segment 0 (80 bytes) at region offset 0 + payload. The 84-byte region is fetched whole in one request — §15.4's "naive reader, unchanged".
  File L, "elevation", coordinate (y,x) = (100000, 70000): t = (390, 273), s = 390·512 + 273 = 199,953; planar C = 1 so disk ordinal k = 199,953; segment σ = 3, covering entries [196608, 262144) = 65,536 entries = **1,310,720 bytes** at region offset 3,932,160; the entry itself at region byte 3,999,060; the CRC array is **16 bytes** at region offset 5,242,880. In-tile position (160, 112) → ordinal 41,072 → the float32 sits at byte 164,288 of the 262,144-byte decoded plane. With a stored payload of, say, 190,000 bytes: **1,500,736 bytes in 3 requests** (CRC array and segment in parallel, then payload) to return four bytes. Every subsequent tile in that segment is then free of index cost, and `[R-LIF-03]`'s (file_id, range) caching never invalidates.
  So: open is O(1) in F and O(layers); the first tile of a large layer is O(segment) = up to 1.25 MiB, bounded at any layer scale (§15.4: "never more than one full segment (1.25 MiB) plus the CRC array, at any layer scale"). That bound is the design's entire index story, and §21.9's 2^32-entry guarantee is sized against it (256 KiB CRC array).

## Findings

### AMBIGUITY — §6.1 `[R-CNT-04]`; §19.1 step 1 `[R-RDR-01]`; §21.2 row F8

Byte-level: True

Whether the 16-byte front signature block must be verified at all is decided by which of two reader classes an implementation belongs to, and the classification test is economic rather than structural. §6.1 defines a **local reader** as "one whose transport serves any byte range at no per-range round trip, a local file or a memory mapping being the ordinary cases" and a **remote reader** as "one whose transport charges a round trip per range"; the local reader "MUST verify the full block by byte equality before other processing and MUST treat any mismatch as reject-file", the remote reader "MAY defer or omit this check". Nothing in the document makes the classification decidable — an mmap of a network filesystem, a loopback HTTP fetch, a caching proxy with a warm local copy, and a reader that has already speculatively pulled a 64 KiB suffix all sit between the two definitions. The consequence is byte-level acceptance: a file whose bytes [0,16) are corrupt is reject-file for one conforming reader and openable by another, and no register row resolves it — §21.2 row F8 lists the detector as an unqualified "reader" with detection point "open", which overstates `[R-CNT-04]`; §21.1's "where a row and the rule it cites diverge, the rule governs" resolves the row but not the class boundary.

**Readings.** (a) Classify by transport type, with the spec's own examples (local file, memory mapping) as the only guidance, and treat everything else as remote — makes the check optional for almost every non-mmap reader. (b) Treat the licence as attaching to the *open path* rather than the transport: a reader that never fetches [0,16) during its open may omit it, and any reader holding those bytes must check. (c) Read "MAY defer" as the operative word for remote readers — the check is owed, only its timing is free. I picked (b): my reader verifies bytes [0,16) by equality whenever they are already resident (local file, mmap, or a speculative suffix window that reached offset 0, i.e. any file ≤ the speculation window), and otherwise never spends a request to obtain them. This is the only reading under which the check is free where it is mandatory and omitted only where it would violate §6.4's request accounting, and it never rejects a file another conforming reader would accept for a reason I could have checked for free.

### AMBIGUITY — §17.2 `[R-COD-07]`; §21.3 row L45

Byte-level: True

`[R-COD-07]` says: "Writers MUST NOT declare this codec for a layer whose tiles' decoded size exceeds 0x7E000000 bytes ... and a reader MUST treat such a declaration as a validity error at layer scope, checkable from declarations alone." In an interleaved layer there is one decoded size, P·Q, and the rule is unambiguous. In a **planar** layer there is no single "the tiles' decoded size": §14.2 gives P·Bᶜ per numeric channel and §14.3 gives ⌈P/8⌉ for a bool channel, so a layer with a float64 channel and a bool channel has two decoded sizes differing by a factor of 64. L45's paraphrase ("a layer whose per-tile decoded size exceeds 0x7E000000") repeats the same singular. A planar layer whose float64 planes are 2.1 GiB and whose bool plane is 33 MiB is accepted or rejected depending on which reading is taken, and the check is layer-scope, so the whole layer turns on it.

**Readings.** (a) Any addressed tile's decoded size exceeds the cap → reject-layer. (b) The maximum over channels exceeds → reject-layer (identical to (a) in every case, since the max is attained by some addressed tile). (c) Every channel's decoded size must exceed before the layer is bad — which would let a layer contain individually undecodable lz4 tiles while remaining valid. (d) The check applies per tile at tile scope rather than at layer scope, contradicting the rule's own stated scope. I picked (a)/(b): compute max over channels of the per-channel decoded size and compare against 0x7E000000, reject-layer on excess. (c) is untenable because it admits tiles that no conforming lz4 decode can produce, and (d) contradicts the requirement's explicit "validity error at layer scope" and its "checkable from declarations alone" claim.

### AMBIGUITY — §17.2 `[R-COD-06]`; §21.4 row T21; Appendix F [RFC 8878]

Byte-level: True

`[R-COD-06]` requires that a writer "MUST NOT declare a window size exceeding the tile's decoded size; a reader MUST treat either as a validity error at tile scope, both being header-checkable." RFC 8878 derives Window_Size two ways: from the Window_Descriptor byte, where the minimum representable Window_Size is 1 KB (windowLog floor 10); or, when Single_Segment_Flag is set, the Window_Descriptor is absent and Window_Size equals Frame_Content_Size. The specification never says which derivation "declared window size" refers to, and the two give different verdicts for every tile smaller than 1024 bytes. This is not hypothetical: §14.2's own worked examples give decoded sizes of 18 and 30 bytes, and §14.3's gives 2 bytes. Under the Window_Descriptor derivation, codec 3 is unusable for any tile under 1 KiB unless the encoder sets Single_Segment_Flag — a constraint the document never states and that a stock streaming encoder will violate by default.

**Readings.** (a) "Declared window size" is Window_Size as RFC 8878 computes it, including the Single_Segment_Flag case — small tiles are conforming only as single-segment frames, and a Window_Descriptor frame over a sub-1-KiB tile is reject-tile. (b) The constraint reads only the Window_Descriptor field, so single-segment frames (which have none) are exempt from it entirely — same practical outcome for small tiles, different outcome for a large single-segment frame whose Frame_Content_Size exceeds the decoded size (already caught by the separate Frame_Content_Size rule). (c) The constraint is a no-op when no Window_Descriptor is present and the 1 KB floor is tacitly excused, i.e. Window_Size is clamped to max(decoded size, 1 KB) before comparison — the reading a lenient implementer would reach for, and the one the text does not support. I picked (a): compute Window_Size per RFC 8878 (Single_Segment_Flag=1 → Window_Size = Frame_Content_Size; otherwise from the Window_Descriptor), compare against the decoded size derived from the layer's declarations, and reject-tile on excess. It is the only reading under which the requirement's "header-checkable" claim is true for every frame shape, and it makes §21.4 T21 exercisable.

### AMBIGUITY — §4.6 `[R-ENC-12]`/`[R-ENC-15]`; §19.1 step 4 `[R-RDR-01]`; §21.2 row F6; §21.3 rows L4, L6, L7

Byte-level: True

Layer-record names are parsed and checked at open (§19.1 step 4: "build the layer table: each layer record's name, parsed and checked per §4.6 (`[R-ENC-12]`). A duplicate layer name is a validity error at file scope, here, at open"), and the register agrees: L4/L6/L7 (ill-formed UTF-8, empty, C0 control in a layer-record name) carry detector *reader*, detection point *open*, outcome **reject-layer**; F6 (two byte-identical layer names) carries detector *reader*, point *open*, outcome **reject-file**. What is never stated is whether a layer whose own name is invalid still participates in the file-scope uniqueness namespace. Both checks fire at the same moment on the same bytes and produce opposite blast radii, so the order of resolution decides the outcome of a file carrying two layers with identical, ill-formed names: reject-file under one reading, two rejected layers and a usable file under the other. §2.4's reject-layer row ("A reader MAY still list the file's layers, including the rejected one's name") assumes a name a reader can hand back, which is exactly what L4/L6/L7 deny.

**Readings.** (a) A layer failing `[R-ENC-12]` is dropped from the namespace before the uniqueness check runs, so its bytes can never trigger F6 — the file survives with fewer usable layers. (b) The uniqueness check runs over the raw name bytes of every layer record regardless of well-formedness — well defined, since `[R-ENC-13]` makes comparison "raw bytes" with no normalization and raw bytes compare fine when ill-formed — and a duplicate is reject-file even when both names are separately invalid. (c) Uniqueness is checked only over the names that passed, but a passing name colliding with a failing one is a duplicate. I picked (b): collect every layer record's raw name byte string at open, run the duplicate check over all of them (reject-file on any collision), then mark each individually-invalid name's layer rejected. `[R-ENC-13]`'s raw-byte comparison rule is total over byte strings, so (b) needs no extra machinery; (a) would let a writer smuggle a name collision past the file-scope check by making both names ill-formed, which inverts the intent of `[R-ENC-15]`'s file-scope outcome.

### CONTRADICTION — §2.3 `[R-CNF-02]` and `[R-CNF-05]` vs §6.3 `[R-CNT-08]` (with §21.6's "conditions that are not violations" table)

Byte-level: False

§2.3 makes file conformance a byte predicate with a closed, enumerated set of conduct-only writer obligations: "File conformance is a pure predicate on bytes ... A few obligations this specification places on writers govern their *conduct* rather than their output — where a value is published, or which registry version a writer targets (§10.3, §18.3) — and a file is never nonconforming by virtue of one: conduct rules bind the actor, the predicate binds the bytes. `[R-CNF-02]`", and "A writer MUST emit only conforming files. `[R-CNF-05]`". §6.3 then imposes a MUST directly on emitted bytes and simultaneously declares the deviating bytes conforming: "In this specification's text no flag bits are defined: a writer creating a file under this text MUST write flags = 0, but a set ignore-lane bit is not a file-conformance violation — such bits are defined by later minor versions, and files carrying them are conforming files this text's readers ignore. `[R-CNT-08]`" (§21.6 concurs: "An ignore-lane flag bit (16–31) is set | Ignored; the file is conforming"). The trailer flags field is output, not conduct, and it is not one of `[R-CNF-02]`'s two enumerated conduct cases (§10.3, §18.3), so a writer can violate a MUST and still, by `[R-CNF-05]`, have emitted a conforming file. Compare how the document treats every other MUST on emitted bytes whose violation leaves reader behavior unchanged — `[R-CNT-12]`'s reserved flag bits ("Both writer violations make the file nonconforming (`[R-CNF-05]`)"), `[R-CNT-22]`'s stored-flag mismatch ("makes the file nonconforming"), `[R-MTA-05]`'s unsorted members ("the file is nonconforming, a verifier MUST report it") — each of which is registered as a verifier-detected violation (F28/F29, F31/L50, F30/L49). The ignore-lane case is byte-identical in shape and lands on the opposite verdict with no stated principle distinguishing it, and consequently has no register row. Practical effect: a verifier cannot decide whether to certify a this-text-generation file carrying a set ignore-lane bit.

### AMBIGUITY — §2.4 `[R-CNF-08]`/`[R-CNF-09]`; §3.2 `[R-MDL-01]`; §19.4 steps 4 and 8 `[R-RDR-04]`

Byte-level: False

In a planar layer a single sample's channel values live in C independent tiles (§3.2: "in a planar layer each channel's storedness is independent, and a single sample can mix decoded and fill values"). §2.4 scopes a reject-tile to "the affected tile's data ... a read of that tile reports failure. All other tiles, including neighbors in the same layer, are unaffected", and `[R-CNF-09]` forbids substituting fill. What the document never states is what a *sample* or *region* request returns when some of its constituent planar tiles are reject-tile and the rest decode cleanly. §19.4 is written per-entry ("Steps 3 through 6 run once per needed entry") and step 8 says only "Return the requested values' bit patterns unaltered" — it never says whether a partially-serviceable sample is a failure or a partial result. The same question arises for any rectangular-region read that covers one damaged tile among hundreds, in either layout.

**Readings.** (a) Any reject-tile among the needed entries fails the whole request — simple, and never returns a partially-populated sample, but throws away megabytes of intact data for one bad tile and reads oddly against §2.4's "All other tiles ... are unaffected". (b) Return the values from every intact tile and report per-tile (hence, in planar, per-channel) failure for the rest, refusing to synthesize anything for the failed positions. (c) Return a whole-sample failure but a partial region — treat the sample as the atomic unit in planar layers, the tile as the unit in interleaved ones. I picked (b): the reader's API returns a result plus a list of failed (disk-ordinal, scope) pairs, and positions belonging to a failed tile are marked unserviceable rather than filled or zeroed. This is the only reading that satisfies both §2.4's "all other tiles are unaffected" and `[R-CNF-09]`'s "a read of a rejected tile MUST NOT silently return fill", and (a) remains available to a caller that wants it. Note (a) is also conforming, so two conforming readers will disagree about whether such a request succeeded — the divergence §14.2's `[R-SER-08]` rationale says the document exists to prevent.

### AMBIGUITY — §2.4 reject-layer row; §8.2 `[R-CNT-20]`; §15.4 `[R-IDX-04]`; §19.2 `[R-RDR-02]`

Byte-level: False

§2.4 defines reject-layer as "The affected layer's data **and metadata** are not usable". But the two failures that produce reject-layer from the index chain — crc_of_crc_array and segment CRC (`[R-IDX-04]`, register rows L38/L39) — are detected at the *tile use* tier (§19.2: "index-chain failures take layer scope (`[R-IDX-04]`) although their detection point is tile use"), whereas that layer's user-metadata sub-record is read at the *extent use* tier and is quarantined so that its own failures never escalate (`[R-CNT-25]`, `[R-MTA-02]`). A reader can therefore legitimately serve a layer's user-metadata document, then later — on the first tile request — discover an index-chain failure that retroactively makes the layer's metadata "not usable". The document does not say whether the earlier service was permitted, whether the reader must retract or invalidate it, or whether the metadata's independent verification survives the layer rejection.

**Readings.** (a) Reject-layer is prospective only: it bars further service, and a document already returned from a separately CRC-verified extent stands, since §8.1 makes the metadata extent's checksum independent of the index chain. (b) Reject-layer is total and retroactive: once it fires, everything about the layer — including a previously returned document — is unusable and must be invalidated in any cache the reader keeps. (c) The metadata quarantine (`[R-CNT-25]`, which overrides the owning-scope mapping of `[R-CNF-08]`) also insulates the document *from* layer-scope rejections, not only from causing them. I picked (a) with a conservative reporting rule: my reader serves the document, and on a later layer rejection reports the layer unusable and stops serving anything further from it, including the document, but does not claim the already-returned bytes were invalid — they were CRC-verified against §8.1's map and are exactly the bytes the writer stored. (b) is unimplementable for a streaming API that has already handed bytes to a caller, and (c) reads more into the quarantine than `[R-CNT-25]` says.

### OBSERVATION — §18.2 `[R-MTA-03]`/`[R-MTA-09]` vs §2.3 `[R-CNF-03]`, §12.1 `[R-TYP-01]`, §17.2 `[R-COD-03]`, §17.3 `[R-COD-09]`

Byte-level: False

The document designates *core* — must-implement — status in exactly three places: sample types (§12.1 "exactly thirteen sample types, all **core**"), codecs (§17.2 "all four are **core**"), and filters (§17.3 "both are **core**"), and `[R-CNF-03]` binds a reader to "every codec and filter that §17 designates as core". The metadata-encoding space of §18.2 is never given that status, and `[R-MTA-03]` explicitly contemplates its absence: "An encoding this specification does not assign, **or one the reader does not implement**, is ignore-record". So a conforming reader that is obliged to implement zstd for tile payloads (codec 3) may nonetheless decline to implement zstd for user-metadata documents (metadata encoding 2) and silently drop every compressed document in the file. This is decidable from the text, but only by noticing that two adjacent uses of the same external format sit in differently-governed identifier spaces (§10.2 lists them as separate rows), and it is expensive to discover because §21's register has no row for it — correctly, since it is not a violation. The practical cost is that user metadata is the one thing in the format whose delivery is not uniform across conforming readers, which §1's "no feature a conforming reader can decline" does not lead an implementer to expect.

### OBSERVATION — §17.4 `[R-COD-11]`, citing "§9.7(d)"

Byte-level: False

`[R-COD-11]` reads: "A verifier that cannot execute a layer's codec or filter cannot establish the layer's conformance and MUST NOT certify the file — the rule of §9.7(d) applied to content." §9.7 is a single unnumbered paragraph carrying `[R-LIF-08]` plus one non-normative Note; it has no lettered or numbered clauses, and no clause (d) exists anywhere in the document (grep for "9.7(" returns this one line). The citation is unresolvable. The requirement is self-contained without it — the sentence before the em-dash states the whole obligation — so nothing is undecidable, but an implementer auditing verifier obligations against their sources hits a dead end, and the analogous obligation in §18.2 `[R-MTA-09]` is stated by pointing at `[R-COD-11]` rather than at §9.7, which suggests the intended anchor is `[R-COD-11]`'s own first clause.

### OBSERVATION — §4.5 `[R-ENC-10]` vs §8.1 `[R-CNT-19]`

Byte-level: False

§4.5 partitions checksum fields into three classes and enumerates the middle one exhaustively: "the terminal checksum fields of §8.1's map — the trailer, directory-region, and user-metadata checksum fields — which are verified by comparison and covered by no further checksum. Interior checksum fields — each segment CRC array and each layer record's crc_of_crc_array — are both comparison-verified and covered by exactly one further checksum, as §8.1 maps." The enumeration omits the fourth checksum field in §8.1's map: a tile-index entry's `crc` field (§15.1, offset 16, 4 bytes), which has exactly the interior character — it is comparison-verified against the CRC-32C of the stored tile's bytes, and it is itself covered by its segment's CRC (§15.4: "the CRC-32C over exactly those entries' bytes as stored"). The coverage invariant of `[R-CNT-19]` ("Every field of every structure is covered by exactly one checksum") still holds, and §8.2's chain of trust lists the entry between the segment and the stored tile, so nothing is undecidable. But an implementer building the verification order from §4.5's taxonomy alone will not find the entry crc in either named class, and will have to reconstruct its position from §8.1's table and §8.2's chain.

### OBSERVATION — §15.4 `[R-IDX-04]`; §7.4 crc_of_crc_array; §21.9's Note

Byte-level: False

The cost of the first cold tile read is decidable but takes assembling four separate statements to see. `[R-IDX-04]` requires, before using entry k, verification of "crc_of_crc_array over the fetched CRC array and the segment CRC over the fetched segment containing k", and `[R-ENC-05]`/`[R-ENC-10]` forbid acting on the entry before both verify. crc_of_crc_array covers the *whole* segment-CRC array (§8.1), and a segment is up to 2^16 entries (§15.4). So reading one sample from a cold large layer costs ⌈entry_count/2^16⌉×4 bytes for the entire CRC array plus up to 65,536×20 = 1,310,720 bytes (1.25 MiB) for one segment, before a single payload byte is fetched — and at §21.9's guaranteed entry_count of 2^32, the mandatory CRC-array fetch alone is 256 KiB. §15.4's worked example and §21.9's Note both state these figures and they are correct, so this is deliberate, not a defect; it is expensive to *derive* from the requirement text because the whole-array scope of crc_of_crc_array is stated in §7.4's field table and §8.1's map rather than in `[R-IDX-04]` itself. An implementer who reads only §19.4 step 3 will under-budget the index path by three orders of magnitude.

Byte-level: False

§21.8 asserts "Every row of §21.2 through §21.5 — 125 conditions over 244 named instances — has at least one conformance vector". Both numbers are load-bearing for `[R-VEC-03]`'s coverage obligation, and both are correct, but confirming them requires mechanically re-counting semicolon-separated cells across four tables under §21.1's counting convention ("Instances within a cell are separated by semicolons, and a cell reading — is one instance"). I also verified the document's three published checksum constants by computing CRC-32C with the §4.5 parameters: CRC-32C("123456789") = 0xE3069283 and CRC-32C(zero bytes) = 0x00000000 (§4.5 check vector); CRC-32C of 65,536 concatenated sentinel entries (`FF`×16 `00`×4, 1,310,720 bytes) = 0xEECB3BB2, matching `[R-IDX-05]`; and CRC-32C over Appendix A's trailer bytes [0,60) = 0xE00938D2, matching the stored bytes `D2 38 09 E0`. Every worked example I checked is internally consistent (§11.2, §11.4, §14.2, §14.3, §14.5, §15.4 both examples, §16.2, §17.3, §20.3, §21.9's Note). ### OBSERVATION — §7.1 `[R-CNT-25]`

Byte-level: False

The rule that governs every user-metadata record's extent is delivered in one sentence whose compound predicate is interrupted by a nested pair of em-dash clauses: "each user-metadata record carries its document in its extent — never inline; an extent of (0, 0) on a user-metadata record, or one whose extent_length is less than 5 — too short to hold both a document and the terminal CRC-32C §8.1 places in its final 4 bytes — is a validity error at its containing scope — and declares the document's encoding in its own inline payload (u8: 0 invalid, 1 = none, 2 = zstd; §18)." The subject's second verb ("and declares") is separated from its subject by 45 words and two levels of parenthetical, and the interposed rule (the (0,0) / extent_length<5 error) is a different requirement about a different actor. The content is recoverable and is restated correctly by register rows F24/F25 and L11/L12 and by §18.1's `[R-MTA-02]`, so nothing is undecidable — but this is the one rule in Part I that I had to read four times to parse, and it carries a scope assignment ("its containing scope") that differs in wording from `[R-CNT-13]`'s "the scope the record governs" for the same slot. The two coincide for both record placements (top-level → file, sub-record → layer), which I confirmed against §7.3's scope table before relying on it.

### OBSERVATION — §9.7 `[R-LIF-08]` vs §5.2 `[R-CNT-02]` and §21.2 row F36

Byte-level: False

§5.2 names five coverage classes — "the front signature block; or a **structure** — a stored-tile extent, a record extent ..., the directory, or the trailer" — and F36 lists "directory region; trailer; front signature block" among the claimants whose overlap a verifier must detect. §9.7's walk, which is the procedure `[R-LIF-08]` gives for checking that partition, enumerates only "the live directory and its records, each record's extent, and each layer's tile-index region together with that region's non-sentinel entries" and then "checks that these occupy disjoint byte ranges, that each lies within [16, F − 64)". The front signature block ([0,16)) and the trailer ([F−64,F)) are coverage classes that are outside that interval by construction and are not in the walk's enumeration, so the walk as written cannot detect an overlap *against* them — which is precisely what the "lies within [16, F − 64)" clause achieves indirectly, since anything satisfying it cannot touch either. The result is correct; the reasoning is left implicit, and a verifier author who implements §9.7 literally and then reads F36's instance list will not see where the front block and trailer are covered.


## Verdict
The document stands alone for a reader implementer. I built a complete conforming reader design — open path, four validation tiers, layer access, the tile-read algorithm including the unstored-tile short-circuit, every degradation path, and byte-exact cold-open accounting at 128 bytes and 4 TiB — without consulting anything outside spec/tarn.md, and without a single place where I had to invent a structure, a byte offset, or an outcome class. The chain of trust (§8.2), the tier ordering (§19.2), and the scope-to-outcome mapping (§2.4) are the three load-bearing rules and all three are stated precisely enough to implement mechanically. Internal consistency is unusually high: I verified all three published CRC constants by computation from §4.5's parameters alone (0xE3069283, 0xEECB3BB2, 0xE00938D2), re-derived §21.8's 125 rows / 244 instances mechanically to an exact match, and hand-checked eleven worked numeric examples without finding an error. Fourteen findings: no defect blocks implementation, and none of the four byte-level ambiguities affects the common path. The two most consequential are `[R-COD-06]`'s zstd window-size constraint, which silently forecloses codec 3 for tiles under 1 KiB unless the encoder sets Single_Segment_Flag — a real interoperability hazard the text never names, and one the spec's own §14.2 examples (decoded sizes 18 and 30 bytes) would trip — and `[R-CNT-04]`'s local/remote reader split, which makes front-signature verification effectively optional for any reader that self-classifies as remote, since the classification test is economic rather than structural. The one contradiction is a classification inconsistency rather than a behavioral one: `[R-CNT-08]`'s "MUST write flags = 0" is a MUST on emitted bytes whose violation §6.3 and §21.6 declare leaves the file conforming, which `[R-CNF-02]`'s pure-byte-predicate framing and its closed list of conduct-only obligations (§10.3, §18.3) do not admit — and every structurally identical case in the document (`[R-CNT-12]`, `[R-CNT-22]`, `[R-MTA-05]`) lands on the opposite verdict with a register row to match. Recommended before acceptance: state the zstd Window_Size derivation and its consequence for small tiles; make `[R-COD-07]`'s cap explicitly max-over-channels; say whether an ill-formed layer name still counts for `[R-ENC-15]`; and either widen `[R-CNF-02]`'s conduct class to cover the flags case or give ignore-lane bits the same nonconforming-file-with-unchanged-reader-behavior treatment the other three cases get.

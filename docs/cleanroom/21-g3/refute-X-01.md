# The finding

**§21.5's capability carve-out still names only "the size bound"; the repair's new window-bound decline is left classed as a violation**

Location: spec/tarn.md §18.2 [R-MTA-09] lines 2466-2473 (the repair) against §21.5's preamble line 3515; and §21.1's completeness clause lines 3283-3291

## Detail

The repair creates a SECOND ground on which a reader or verifier may decline a metadata document as its own capability rather than as a fault in the file: the window bound. §21.5's preamble is the document's only other statement of that capability/violation line, and it enumerates its exceptions closed. It says every way a document can be unreadable takes ignore-record "as a violation in the rows below", with exactly two exceptions: an experimental-range encoding, and "where a reader or verifier declines the decode on the size bound". A window-bound decline is neither. So §21.5 leaves it inside the general clause — a violation — while §18.2 as repaired says in terms it is "no violation". The two texts are flatly opposed on the same fact.

The collision is not curable by reading §21.5 charitably, because it fails twice over. If the window-bound decline IS a violation, §21.1's completeness clause is breached: "Its **completeness is normative** — a *detectable* file-conformance violation this specification names and the register omits is a defect in this document", and no row R1-R10 covers it. R3 is expressly disclaimed by the repair; R4's instances enumerate the frame constraints and the window is not among them. If it is NOT a violation, §21.5's preamble is simply wrong and §21.6 — which the preamble points at as the place non-violations live ("§21.6 lists the ignore-record conditions that are not violations") — has no entry for it either.

This is exactly the shape the charter names as the project's most common defect and the shape a single-hunk auditor structurally cannot catch: the repair is 1,045 lines away from the text it contradicts, and my whitespace-normalised search shows the contradicting text is the ONLY other place the rule is stated, so nothing else in the document reconciles them.

What an implementer does wrong without this: a verifier written from §21.5 reports *nonconforming* for a file whose metadata frame declares a window above the verifier's ceiling. A verifier written from §18.2 reports *cannot establish* and MUST NOT certify, or *conforming* if it decoded. Both authors are reading normative text.

## Text complained about

The frame's declared `Window_Size` is unconstrained here for the same reason, and takes the same treatment: a reader's window bound is its own, no smaller than §21.9's guarantee for that quantity, and a frame declaring more than the reader admits is ignore-record on that ground — the reader's capability, not a failure to decode within the meaning of R3, and no violation (`[R-MTA-09]`, `[R-ERR-03]`).

## Contradicting text

spec/tarn.md line 3515, §21.5 preamble, normative prose (not a blockquote): "User metadata is quarantined (`[R-CNT-25]`): every way its document can be unreadable takes this outcome, whatever the containing scope — as a violation in the rows below, except at an experimental-range encoding, where no document rule attaches and §21.6 records the defined non-violation (`[R-MTA-10]`), and except where a reader or verifier declines the decode on the size bound, which `[R-MTA-09]` makes that actor's capability and not a fact about the file." ... and, closing the same paragraph: "Every row here is a violation all the same: the outcome bounds a reader's blast radius and never makes the file conforming (`[R-CNF-12]`); §21.6 lists the ignore-record conditions that are not violations."

## Auditor's byte-level rationale

The disputed file is conforming — nothing bars a writer from emitting a metadata frame declaring a large window, since the repair makes Window_Size unconstrained there and §21.9's table states guarantees, not caps. So the [R-CNF-05] escape does not apply: this is not a file that carries a register-row violation under both readings. The two readings fork an actual verdict on identical bytes. Implementation A follows §21.5 and, on encountering a metadata frame declaring a 32 MiB window with its ceiling at 8 MiB, records a violation and reports the file *nonconforming*. Implementation B follows §18.2 as repaired and reports the decline as its own capability, verdict *cannot establish*, expressly "not a finding that the file is nonconforming". Same bytes, opposite certification verdicts, both implementers reading normative text. If the maintainer instead resolves it by adding a §21.5 row, the emittable set itself moves, because a registered violation puts the file outside [R-CNF-05] and bars every conforming writer from emitting that frame.

# The downgrade you must attack

Graded **REFUTED**, not byte-level. Its reasoning:

The auditor's quotations are accurate and in context — §18.2 lines 2466-2473 and §21.5's preamble line ~3515 say what they are reported to say. But the finding rests on one load-bearing empirical claim that is false, and on two subsidiary arguments that the document expressly forecloses.

1. THE "ONLY OTHER PLACE" CLAIM IS FALSE. The auditor writes: "§21.5's preamble is the document's only other statement of that capability/violation line" and "my whitespace-normalised search shows the contradicting text is the ONLY other place the rule is stated, so nothing else in the document reconciles them." The search that would have found the reconciling text is not a search for "size bound" — it is a search for the *decline*. §2.3's [R-CNF-11], at line 202, enumerates the verifier's *cannot establish* grounds and includes, with no qualification as to which bound: "or when it declines to decode a user-metadata document (`[R-MTA-09]`)". That clause ranges over every [R-MTA-09] decline, size bound and window bound alike, and the same requirement then states "*Cannot establish* is not a finding that the file is nonconforming." That is normative prose in the definitions section, not a blockquote, and it fixes precisely the verdict the auditor says is forked.

2. §21.9's [R-ERR-04] INDEPENDENTLY FIXES IT, AND ITS TABLE NAMES THE WINDOW. The §21.9 limits table (line ~3673) carries the row "zstd frame `Window_Size` | 8 MiB". [R-ERR-04] then says at line 3676: "A file exceeding any of these remains conforming, and a reader MAY decline it", and at 3683: "a refusal on resource grounds MUST be reported as a resource limit and not as a validity error: the two send a user to opposite remedies, and a reader that reports 'too large' as 'corrupt' invites the deletion of intact data." The auditor's Implementation A — recording a violation and reporting *nonconforming* on a 32 MiB declared window against an 8 MiB ceiling — is doing exactly the thing this MUST NOT-in-substance forbids. It is not a reading of normative text; it is a breach of one. [R-CNF-03] at line 162 routes there explicitly: the reader's acceptance duty runs only to a file "none of whose values exceeds the minimum guarantees of §21's limits table (§21.9's `[R-ERR-04]` governs a refusal on that last ground)."

3. THE PARALLEL TILE CASE ALREADY SETTLES THE PATTERN. [R-COD-06] at line 2293-2297 does for tiles what the repair does for documents: "Writers SHOULD keep the declared window within §21.9's 8 MiB `Window_Size` guarantee even for a larger tile; a wider window is conforming and merely permits a conforming reader to decline the tile or the layer on resource grounds (`[R-ERR-04]`)." So "wider window declared = conforming file, decline is resource-grounds" is settled doctrine in this document, stated before §18.2 and independent of it. The repair is conforming its passage to the house rule, not inventing a second ground out of nothing.

4. THE PREAMBLE'S CLAUSE ROUTES TO ROWS, AND THERE IS NO ROW. The preamble sweeps "as a violation **in the rows below**". A verifier records violations against rows. The auditor correctly establishes that no row reaches this case (R3 is disclaimed by §18.2 in terms — "not a failure to decode within the meaning of R3"; R4's constraint set is the six non-tile [R-COD-06] constraints and its Instances cell enumerates exactly those six, window absent). So the sweep dead-ends: it points at rows that do not exist. §21.1 supplies the tie-break for exactly this posture — "each row *restates* its governing rule, and where a row and the rule it cites diverge, **the rule governs**" — and the preamble's own carve-out is defined by citation, not by the noun phrase: "which `[R-MTA-09]` makes that actor's capability and not a fact about the file." [R-MTA-09] makes both bounds that actor's capability. Read with its own citation, the carve-out reaches the window bound.

5. BOTH HORNS OF THE AUDITOR'S FORK FAIL. (a) Completeness: §21.1's clause bites on "a *detectable* file-conformance violation this specification names and the register omits". The specification does not name this as a violation — [R-MTA-09] names it "no violation" — so nothing is omitted and the clause is not breached. (b) §21.6: §21.1 forecloses this directly at lines 3308-3312: "The subsections after §21.5 are not part of the register and carry no rows: neither this completeness clause nor the instance arithmetic below reaches §21.6's defined non-violations..." §21.6 has no normative completeness, so an absent entry is not a defect. Confirming this is by-design rather than an oversight the repair created: I read §21.6's table in full and it has no entry for the **size**-bound decline either — the exception the preamble does name, and which predates this repair. Neither belongs there, because §21.6 lists conditions of the *file*, and both texts say a bound decline is the actor's capability "and not a fact about the file."

RESIDUAL, AND WHY IT IS NOT THE FINDING. The one true observation left is editorial: §21.5's preamble says "the size bound" where [R-MTA-09] now has two bounds, so a copy-edit to "on a bound of its own" or "on a resource bound" would read better. Nothing normative turns on it — the verifier verdict is fixed by [R-CNF-11], the reporting duty by [R-ERR-04], the row question by §21.1 — so it does not rise to a defect, and I grade REFUTED rather than PARTIAL. I searched hard for the opposite conclusion: I checked whether a writer rule bars the wide window for documents (none exists), whether R3 or R4 could reach it (neither does), whether §21.6 must carry it (§21.1 says no), and whether any text anywhere makes the window decline a violation (whitespace-normalised search for "window bound" returns exactly one occurrence, the repair itself).

BYTE-LEVEL, INDEPENDENTLY. I agree the disputed file is conforming and emittable: no writer requirement constrains a metadata frame's declared Window_Size, and §21.9's table states guarantees, not caps. But conformance alone is not the test — the test is whether two implementers reading normative text reach opposite certification verdicts on those bytes. They do not. [R-CNF-11] tells the declining verifier its verdict is *cannot establish* and that this "is not a finding that the file is nonconforming"; [R-ERR-04] tells the declining reader the refusal "MUST be reported as a resource limit and not as a validity error." An implementation reporting *nonconforming* is not exercising a second permissible reading; it is nonconforming as a verifier. No fork. Answer: no.

# The finding

**For a single-segment frame Window_Size IS the decoded size, so the new 8 MiB bound silently caps §21.9's 16 MiB document guarantee**

Location: spec/tarn.md §18.2, the repair at lines 2466-2473 against the untouched Note at lines 2488-2497 three lines below it, and against §21.9's table rows at 3674-3675; mechanism stated at §17.2's Note, lines 2299-2304

## Detail

The repair justifies the new rule with "for the same reason" — the reason, stated in the sentence immediately above it, being that "a document has no declared size". That reason is false for a whole class of conforming frames, and the document says so elsewhere. §17.2's Note: "with Single_Segment_Flag set there is no Window_Descriptor and Window_Size is the frame content size". For a single-segment metadata frame the document DOES declare a size, in Frame_Content_Size, and Window_Size is that number.

The consequence is that the repair's new bound and the pre-existing decoded-size bound measure the same quantity for such frames, but §21.9 gives that quantity two different guarantees: "decoded size of one user-metadata document | 16 MiB" and "zstd frame `Window_Size` | 8 MiB". A 12 MiB document stored as a single-segment frame is within the 16 MiB row and above the 8 MiB row simultaneously. Before the repair, only the 16 MiB row was in play for a metadata document and the guarantee meant what it says. After the repair, a reader with its window ceiling at the 8 MiB floor may ignore-record that document. The 16 MiB row becomes unreachable for encoding-2 single-segment documents above 8 MiB — the larger guarantee is silently dead in the case the format's own Note says small documents are FORCED into ("the Window_Descriptor cannot express less than 1 KiB", so sub-1-KiB documents must be single-segment; nothing pushes a writer off single-segment as sizes grow).

The untouched Note three lines below the repair is written to be true only under the old wording. It reasons: "A file whose document decodes to more than the guarantee stays conforming, and it falls outside `[R-CNF-03]`'s acceptance duty" — implying the converse, that a document decoding to 16 MiB or less is inside the duty and must be accepted. The repair falsifies that for single-segment frames above 8 MiB. The same Note then reasons from "a document having no declared size and so no narrower scope whose declarations that rule can measure" — precisely the premise the repair's own subject matter contradicts, since Window_Size is a declaration in the frame header.

Without this, an implementer reading §21.9's table believes a 12 MiB metadata document is universally readable, and it is not.

## Text complained about

The frame's declared `Window_Size` is unconstrained here for the same reason, and takes the same treatment: a reader's window bound is its own, no smaller than §21.9's guarantee for that quantity

## Contradicting text

spec/tarn.md lines 2488-2497, §18.2's Note (non-normative, but the passage's stated reasoning): "**Note.** The 16 MiB figure is a §21.9 minimum guarantee, so the two rules compose here as they do elsewhere. A file whose document decodes to more than the guarantee stays conforming, and it falls outside `[R-CNF-03]`'s acceptance duty, which runs only to a conforming file none of whose values exceeds those guarantees. ... a reader that instead declines on resource grounds under `[R-ERR-04]` does so at the whole file, a document having no declared size and so no narrower scope whose declarations that rule can measure." And the mechanism, spec/tarn.md lines 2300-2302, §17.2's Note: "with Single_Segment_Flag set there is no Window_Descriptor and Window_Size is the frame content size".

## Auditor's byte-level rationale

The disputed file is conforming under every reading — the repair makes Window_Size unconstrained for documents, so no writer rule and no register row bars it, and [R-CNF-05] does not bite. Take a 12 MiB user-metadata document stored under encoding 2 as one single-segment zstd frame, so Frame_Content_Size = Window_Size = 12 MiB. Reader A sets its window ceiling at 8 MiB, the §21.9 floor the repair permits, and takes ignore-record: the record is skipped as though absent and the application sees no metadata. Reader B sets its ceiling at 16 MiB and returns the document. Both are conforming, because [R-CNF-03]'s acceptance duty reaches only files "none of whose values exceeds the minimum guarantees" and this file's Window_Size exceeds one. The verifier side forks too: A must not certify and reports *cannot establish*; B certifies *conforming*. On the writer side the emittable set moves in the sense that matters to a writer: to produce a >8 MiB metadata document every conforming reader must accept, a writer must now avoid the single-segment framing and emit a Window_Descriptor — a different byte in the frame header for the same document.

# The downgrade you must attack

Graded **REFUTED**, not byte-level. Its reasoning:

The finding rests on three premises, and the document decides all three against it.

1. The Note the auditor says is "written to be true only under the old wording" is already written conjunctively, and the auditor quoted the words that refute their own reading. Line 2490-2492: "it falls outside `[R-CNF-03]`'s acceptance duty, which runs only to a conforming file **none of whose values exceeds those guarantees**." Not "whose document decodes within the guarantee" — *none of whose values*, over the whole table. [R-CNF-03] itself (lines 162-163) states the condition the same way: "none of whose values exceeds the minimum guarantees of §21's limits table". So a 12 MiB single-segment metadata frame, whose Window_Size value is 12 MiB, is outside the acceptance duty by the Note's own quantifier. The Note is not falsified; it correctly covers exactly the auditor's case. The claimed implied converse ("a document decoding to 16 MiB or less is inside the duty and must be accepted") is a misreading — the duty's antecedent is a conjunction over all quantities, not over the document's decoded size alone.

2. The repair did not introduce the interaction; it was already there, and §21.9's row was never tile-scoped. Pre-repair, §18.2 imported only "the frame constraints of `[R-COD-06]` that do not reference a tile" and enumerates them: magic, no skippable/second frame, no nonzero dictionary ID, no content-checksum flag. [R-COD-06]'s window clause ("MUST NOT declare a window size exceeding the tile's decoded size") references a tile, so it was excluded before the repair too — Window_Size was already unconstrained for documents by omission. Meanwhile §21.9's row reads "zstd frame `Window_Size` | 8 MiB" with no tile restriction, and [R-CNF-03]'s conjunction already reached it. So the acceptance duty for a 12 MiB single-segment metadata document was already not universal before the repair. The repair changes no file's classification and no reader's acceptance duty; it names the window explicitly and routes the reader's decline to ignore-record (per-record) rather than leaving it to an [R-ERR-04] whole-file decline. The "16 MiB row becomes unreachable" harm is not caused by the repair.

3. The same composition is stated as designed for tiles, three sections earlier, in untouched text. §21.9 gives "decoded size of one tile | 256 MiB" and "zstd frame `Window_Size` | 8 MiB", and [R-COD-06] at lines 2293-2296 spells out the consequence: "Writers SHOULD keep the declared window within §21.9's 8 MiB `Window_Size` guarantee even for a larger tile; a wider window is conforming and merely permits a conforming reader to decline the tile or the layer on resource grounds". By the auditor's own mechanism (§17.2's Note: single-segment ⇒ Window_Size = frame content size = tile decoded size), a 256 MiB single-segment tile has a 256 MiB window and is likewise outside the acceptance duty. The document treats guarantee rows as a conjunction of floors and says so twice; it does not treat the larger row as a standalone promise. Appendix line 4071 restates them as one conjunctive list ("16 MiB metadata document · 8 MiB zstd window").

On the "for the same reason" charge: the reason is sound. The §17.2 constraints in question measure against *the tile's declared decoded size*, which comes from the layer's declarations (§14, `[R-SER-07]`) — both the window clause and the "content-size field ... MUST equal the tile's decoded size" clause need that external declaration to exist, and §17.2 justifies the window rule precisely as "both being header-checkable". A document has no such declaration, so neither clause is statable or header-checkable for it. Frame_Content_Size does not supply the missing term: it is the very thing §17.2 has to check *against* the declared size, not a substitute for it. The auditor's second Note limb fails for a further reason: "no narrower scope whose declarations that rule can measure" is about [R-ERR-04]'s scope ladder, whose narrow scopes are enumerated as "a layer or a tile" — a user-metadata record is neither, whatever the frame header contains. And the repair's window decline is not an [R-ERR-04] decline at all; it is ignore-record under `[R-MTA-09]`/`[R-CNT-25]`, mirroring the untouched sentence immediately above it ("a document exceeding that bound is ignore-record like any other it cannot read").

Register check: §21's metadata rows R1-R4 assign no window outcome — R4 enumerates exactly the imported constraints and omits window; T21 ("the frame declares a window size larger than the tile's decoded size") is explicitly tile-only. So no row contradicts the repair, and §21.1 is not engaged.

What I searched for and did find, so the absence-of-deciding-sentence route does not apply: the deciding sentences are [R-CNF-03] line 162-163, §18.2's Note line 2491-2492, §21.9's [R-ERR-03]/[R-ERR-04] at 3676-3681, and [R-COD-06] at 2293-2296.

Residual, and not enough to move the verdict off REFUTED: §18.2 has no writer-side counterpart to [R-COD-06]'s "SHOULD keep the declared window within §21.9's 8 MiB guarantee". A writer aiming at universal acceptance must infer that from [R-CNF-03]'s conjunction rather than being told. That is a guidance gap of the same shape the tile rule closes with a SHOULD — an improvement the repair could have made, not a contradiction it created, and not the defect as described.

Byte-level, independently: no. The auditor concedes the disputed file "is conforming under every reading", and the emittable set is unchanged — both the single-segment framing and the Window_Descriptor framing were conforming before and after. The reader fork A/B is not defect-induced divergence: it is the floor architecture working as written, licensed identically by the untouched preceding sentence (decode bound "of its own choosing, no smaller than §21.9's user-metadata guarantee") and by [R-CNF-03]'s conjunctive quantifier, which predates the repair. Two conforming readers already diverge on a 20 MiB document; that is what "minimum guarantees, not caps" means.
